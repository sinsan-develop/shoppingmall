# S6 정산 후속 계약 대조표

> 범위: `WORK_PLAN_20260-10-09.md` B2. 이 문서는 승인된 A1·A2 권고안을 현재 C1·C2 구현과 대조하는 검토 자료다. 기존 설계서·작업계획서를 대체하지 않는다. 아래 UUID와 금액은 설명용 가상값이며 실제 DB 행이나 계정 정보가 아니다.

## A1: 원장 정정 사건

| 항목 | 기존 S6 | 후속 계약 |
|---|---|---|
| 잘못된 수수료 사건 | 원행 불변, 정정 입력 경로 없음 | 원행을 수정·삭제하지 않고 별도 `correction` 사건 추가 |
| 금액 | 원장 사건의 양의 정수 원화 금액 | 양의 `amountWon`과 `increase`/`decrease` 방향을 분리 저장. 조회 소계에서 원항목 종류에 부호를 적용 |
| 근거 | 원주문·판매자·발생일 | `originalEventId`, 관리자, 사유, 요청 UUID, 서버 기록 시각을 보존. 원사건의 판매자·당시 분류·상품/주문 근거를 조회에 연결 |
| 중복/경합 | 수동 수수료 요청 ID로 중복 차단 | 동일 UUID·동일 본문은 같은 사건 반환, 다른 본문은 409. 같은 원사건을 잠근 거래로 초과 감소·동시 감소 방지 |
| 지난 기간 | 기간 확정 당시 연결 사건·항목 금액 고정 | 확정 뒤 입력한 정정은 새 발생 사건이며 이미 고정된 금액은 바꾸지 않음 |

관리자만 `POST /admin/settlement/corrections`에 JSON 본문을 보낸다. 예시:

```json
{
  "originalEventId": "11111111-1111-4111-8111-111111111111",
  "requestId": "22222222-2222-4222-8222-222222222222",
  "direction": "decrease",
  "amountWon": 2000,
  "reason": "수수료 오입력 정정"
}
```

새 기록 응답은 HTTP 201이며 `id`, `originalEventId`, `requestId`, `direction`, `amountWon`, `reason`, `occurredAt`을 반환한다. 비로그인 401, 판매자 403, 형식 오류 400, 요청 UUID 본문 충돌 또는 원금액 초과 감소 409다. 유효하지 않거나 접근 가능한 비정정 원사건이 없으면 현 구현은 403을 반환한다. 요청 Origin 검사와 서버 세션 권한을 재사용하며 임의 판매자 ID·항목 종류·발생 시각은 요청에서 받지 않는다.

금액 예: 5월 수수료 10,000원 사건을 5월 기간에 고정한 뒤 7월 2,000원 감소 정정을 기록하면 5월 고정 수수료는 10,000원, 7월 정정 사건은 2,000원, 두 사건을 포함한 기간의 수수료 순소계는 8,000원이다. 이는 농가 지급액 또는 자동 송금액을 뜻하지 않는다.

## A2: 판매자 분류 변경 이력

| 조회 | 분류 X 당시 사건 10,000원 | 분류 Y 당시 사건 3,000원 | 기간 확정 표시 |
|---|---:|---:|---|
| 전체 | X·Y 사건을 같은 판매자 구획에 구분 | 포함 | 연결된 전체 사건의 항목별 고정 금액 13,000원 |
| 분류 X | X 사건만 | 제외 | X에 연결된 고정 부분 금액 10,000원 |
| 분류 Y | 제외 | Y 사건만 | Y에 연결된 고정 부분 금액 3,000원 |
| 개별 판매자 | X·Y 사건을 같은 판매자 구획에 구분 | 포함 | 기간 전체의 고정 금액 13,000원 |

관리자 `GET /admin/settlement?from=YYYY-MM-DD&to=YYYY-MM-DD`에 `categoryId` 또는 `sellerId`를 선택적으로 붙인다. 반환되는 `groups`·`totals`는 조회 기간에 발생한 사건, `lateGroups`·`lateTotals`는 해당 기간 안에서 과거 확정 연결에서 빠진 늦은 사건, `completions[].frozenTotals`는 당시 연결된 사건의 항목별 금액이다. 분류 필터를 주면 `frozenTotals`는 그 분류에 해당하는 연결 사건의 **부분 금액**이다. 화면의 기간 확정 입력은 판매자 한 명과 전체 기간에 적용되며, 분류 필터가 별도의 분류 단위 확정을 만들지 않는다. 판매자는 `GET /seller/settlement?from=...&to=...`에서 자기 자료만 읽고 `categoryId`·`sellerId`를 직접 지정할 수 없다.

사건이 하나도 연결되지 않은 0원 기간은 기간 기록 당시의 판매자 분류 스냅샷으로 조회한다. 과거에 이미 저장된 기간의 분류를 현재 분류로 조용히 소급하지 않는다. `0023`은 기존 기간 행이 있으면 적용을 거부한다.

## DB 영향·복구 경계

- `0022_s6_corrections.sql`은 `settlement_events`에 원사건 FK와 방향 열, 원사건 인덱스·입력 검증 트리거를 추가한다. 기존 0020·0021 SQL과 원장 행은 변경하지 않는다.
- `0023_s6_completion_category.sql`은 기간 테이블에 분류 ID·이름 스냅샷을 추가한다. 기존 기간 행이 있으면 이관안 없이 실패하며, 공유 DB 사전 확인이 필요하다.
- 두 파일은 추가식 migration이다. 공유 `local-postgres/shoppingmall` 적용은 이 문서나 계획 승인만으로 허용되지 않으며 대상·백업·복구 대조 후 별도 환경 승인을 따른다. 격리 DB 검증과 공유 DB 행 검증을 같은 증거로 표시하지 않는다.
- 코드 회귀 시 이전 검증 버전으로 revert PR을 사용한다. 이미 생성된 불변 사건·기간·연결 행을 삭제하거나 역마이그레이션하지 않는다. 영속 DB 복원은 영향 범위와 백업을 확인한 별도 승인 절차다.
