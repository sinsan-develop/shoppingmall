# 어울몰 고객 찜·옵션별 재입고 신청 설계

- 상태: 신산님 서면 검토 대기 (2026-09-29). 제품 코드·DB migration 적용 승인/검증 완료 문서가 아니다.
- 정본 연결: [승인된 제품 설계 R04·R10·R12](../../design/DESIGN.md), [개발 계획 S2.4·S5.3](../../WORK_PLAN.md), [작업현황](../../../WORK_STATUS.md).
- 사용자 결정: 찜은 상품 단위, 재입고 신청은 옵션 단위. 재입고 알림은 한 번 전달된 뒤 신청을 종료한다. 실제 발송 채널 연동은 S5/UAT 경계에 둔다.

## 1. 목적·완료 경계

고객은 로그인 계정에서 공개 상품을 찜·해제하고, 품절된 특정 옵션의 재입고 알림을 신청·취소하며, 다른 기기에서도 자기 내역을 조회할 수 있다. 판매자와 관리자는 타 고객의 찜·신청을 조회하거나 대신 변경하지 않는다. S2.4의 완료는 신청 정보의 저장·조회·취소 및 화면 상태까지이며 문자·메일·푸시 발송 성공을 뜻하지 않는다. S5.3에서 알림 작업과 수신 동의·재시도·중복 억제를 연결한다.

개인화 추천, 브라우저 저장소를 거래 정본으로 사용, 실제 연락처 복제 저장, 외부 발송 공급자 연동은 이 범위에 넣지 않는다.

## 2. 비교한 방식과 선택

1. **고객 계정에 상품 찜과 옵션 신청을 별도 저장(채택):** 기기 간 일치, 서로 다른 수명·중복 규칙을 각각 표현한다. PostgreSQL의 추가 테이블·migration과 고객 API가 필요하다.
2. 하나의 범용 `고객-상품 활동` 테이블: 테이블 수는 줄지만 찜에는 없는 옵션·알림 상태를 다수의 빈 필드와 조건부 제약으로 표현해야 한다. 권한·이력 해석이 복잡해 채택하지 않는다.
3. 브라우저 로컬 저장만 사용: DB 변경은 없지만 다른 기기와 일치하지 않고 S5 알림 대상을 신뢰할 수 없어 채택하지 않는다.

## 3. 저장 대상과 불변식

- `customer_favorites`: 고객 계정 ID와 **상품 ID**의 한 쌍이 현재 찜 상태다. 같은 쌍의 중복 생성은 없고 해제 후 다시 찜할 수 있다. 상품의 현재 공개 개정이 바뀌어도 상품 ID를 유지한다.
- `restock_subscriptions`: 고유 신청 ID, 고객 계정 ID, 상품 ID, 판매자가 등록한 **옵션명**, 신청·취소·알림 완료 시각과 상태를 보존한다. S2에서 만들 수 있는 상태는 `active`와 `cancelled`이며 `notified`는 S5의 실제 전달 확정 처리에서만 사용한다. 같은 고객·상품·옵션명의 `active` 신청은 최대 한 건이다. 취소·알림 완료 뒤 다시 품절되면 새 신청을 만들 수 있고 과거 행은 보존한다.
- 화면/API는 현재 공개 옵션 ID를 입력으로 받더라도 서버가 해당 공개 개정에서 옵션명을 확인해 저장한다. 고객이 옵션명을 임의로 전달해 다른 상품에 신청하지 못한다. 상품 수정으로 옵션 ID가 바뀌어도 **같은 상품·같은 옵션명**이면 신청이 이어진다. 옵션명이 바뀌거나 없어지면 그 이름의 옵션이 현재 공개되지 않은 동안 알림은 발송하지 않으며 고객에게 `현재 없는 옵션`으로 표시하고 취소를 허용한다.
- 새 재입고 신청은 현재 공개 상품의 해당 옵션이 판매 가능 0개이고 상품 자체가 판매중지 상태가 아닐 때만 받는다. 기존 신청은 상품이 품절·판매중지·비공개가 되어도 임의 삭제하지 않지만 그 상태에서는 발송하지 않는다. 찜은 공개 이력이 있는 상품의 판매중지 상태를 표시하며 과거 찜을 임의 삭제하지 않는다.
- 새 테이블에는 전화번호·이메일·발송 비밀값을 복제하지 않는다. 계정 삭제·시험자료 reset은 자식 행을 정확한 계정/상품 범위에서 먼저 정리한다. 운영 보관·파기 기간은 기존 개인정보 정책의 별도 검토를 따른다.

## 4. API·화면 흐름

- 고객 전용 API: 자기 찜 목록 조회, 공개 상품 찜 추가/해제, 자기 재입고 신청 목록 조회, 공개 품절 옵션 신청, 자기 신청 취소. 변경 요청은 기존 세션·활성 역할·Origin 검사를 사용한다. 상품/옵션·신청 ID는 서버에서 소속과 현재 공개 상태를 다시 확인한다. 판매자·관리자 역할, 다른 고객의 신청 ID, 비로그인 요청은 거부한다.
- 같은 찜/재입고 추가 요청을 재시도해도 활성 행은 하나만 남고 추가 감사 기록을 만들지 않는다. 없는 찜/자기 신청 취소는 화면에서 현재 상태로 갱신 가능하도록 멱등 처리한다. 유효하지 않은 상품·옵션, 판매 가능 옵션 신청, 권한 없음은 구분된 오류로 돌려준다.
- 실제 찜 추가·해제, 재입고 신청·취소는 고객 계정·활성 역할·대상·시각을 기존 감사 이력에 남긴다. 멱등 재시도는 상태와 감사 기록을 중복 변경하지 않는다.
- 고객 상품 상세에는 `찜/찜 해제`와 품절 옵션마다 `재입고 알림 신청/취소`를 둔다. 로그인 전 선택하면 로그인 필요를 안내하고, 서버 응답 전에는 완료 문구를 보이지 않는다. 고객 계정에는 찜 목록과 옵션별 신청 목록·상태·취소 동선을 둔다. 품절·판매중지·현재 없는 옵션을 구별한다. 기존 Flat v2 색·서체·키보드 포커스 패턴을 유지한다.
- 데이터 로딩/연결 실패 시 저장됐다고 추측하지 않고 재시도 안내를 표시한다. 공개 상품 검색·결제 화면의 장애로 전파하지 않는다.

## 5. S5 알림 연결 계약

재고의 **판매 가능 수량**이 0에서 양수로 바뀌고 해당 상품/옵션이 여전히 공개·판매 가능해진 사건만 재입고 후보가 된다. 보유 수량 증가만으로는 후보가 아니다. 승인 전 재고 증가, 동일 상품의 다른 옵션 증가, 판매중지, 비공개 개정의 증가는 후보가 아니다. S5의 알림 작업이 활성 신청을 식별하고 채널 동의·전송 성공을 확인한 뒤에만 `notified`로 닫는다. 실패 시 재시도하며 같은 신청 ID의 중복 발송을 억제한다. S2는 이 사건 연결에 필요한 신청 식별·상태 계약만 마련하고 실제 발송·완료 처리 또는 공급자 성공을 주장하지 않는다.

## 6. 구현·검증 경계

- 대상: 기존 `apps/api/src/customer/`, `apps/api/src/db/schema.ts`와 신규 additive migration, 상품 상세·고객 계정 화면, API/DB/웹 시험, 고유 QA fixture reset. 인증 체계·상품 공개/재고 결정 규칙은 변경하지 않는다.
- RED→GREEN: 타 고객·판매자·관리자 접근 거부, 공개 전/잘못된 옵션/판매 가능 옵션 신청 거부, 동일 요청 동시 접수 1건, 취소 후 재신청과 이력, 같은 이름의 새 상품 개정에서 신청 유지, 사라진 옵션/판매중지에서 발송 후보 제외, 고객 화면 로딩·오류·키보드 경계를 시험한다.
- migration은 현재 Drizzle 이력을 읽기 전용 dry-run으로 대조한 뒤 별도 임시 DB에서 전체 적용·회귀를 먼저 시험한다. 승인된 `WSL-server`의 `local-postgres/shoppingmall` 개발 DB에만 그 동일 migration을 적용한다. 기존 실제 데이터는 초기화하지 않는다. 로컬 unit/typecheck/lint/build, 지정 WSL checkout exact SHA의 DB/API·실제 브라우저 검증 후 시험 계정·상품·신청·컨테이너 잔류를 확인한다.
- 장애/복구: 새 화면/API를 비활성화해 기존 공개 카탈로그를 유지할 수 있게 한다. 적용한 migration을 무조건 역삭제하거나 고객 신청 기록을 지우지 않는다. 문제의 원인·행 영향·복구 방법을 기록하고 안전한 후속 migration/코드로 수정한다. S2 기능 시험은 Oracle·실알림·사용자 인수 합격이 아니다.
