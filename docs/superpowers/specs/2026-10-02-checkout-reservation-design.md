# S3.1 주문 직전 15분 재고 예약 설계

상태: **신산님 검토 초안**. 예약 구현·공개 API·DB migration·공유 개발 DB 적용을 승인한 문서가 아니다. 기준은 기존 `docs/design/DESIGN.md` R02~R05, `docs/WORK_PLAN.md` S3, `2026-10-02-account-cart-design.md`, 작업 브랜치 `codex/flat-v2-prototypes@c0621839ca720e0c2fd4391017b31d9b4982e8d9`이다.

## 목적·결정과 비범위

- 고객이 장바구니에서 결제를 시작할 때만 서버가 옵션 수량을 최대 15분 보전한다. 장바구니 담기·수정·일반 견적은 예약하지 않는다.
- 신산님은 판매자가 예약 도중 재고 0을 입력해도 **새 구매를 즉시 차단하고 기존 예약은 만료까지 유지**하는 방향으로 진행하도록 했다. 예약 종료 후 입력한 0을 반영한다. 보낼 실물이 없는 예외는 운영자가 사유를 남기고 예약을 취소한다.
- 예약은 **수량만 보전**하며 가격·할인·배송비·결제 성공을 보장하지 않는다. 주문 접수와 결제 대조에서 서버 금액을 다시 확인한다. PG, 실제 결제, 할인 배분, 발송 주문 저장, 환불은 이 단위의 구현 범위가 아니다.
- 예약 만료 시각은 DB 시각으로 생성한다. 고객 기기 시계, 브라우저 타이머, 임시 메모리 저장은 판정 근거가 아니다.

## 검토한 방식과 선정 이유

1. **별도 예약 원장 + 기존 재고 행 잠금(권장)**: 예약 행을 보존하고 현재 판매 가능 수량에서 만료 전 예약분을 계산해 제외한다. 판매자의 0 입력은 공개 판매를 즉시 닫되 예약분의 보유 수량은 보전하고, 0 목표를 종료 후 적용한다. 동시 구매·감사·재시작 복구가 가능하다.
2. 기존 `inventory_levels` 수량만 예약 시 차감: 새 표는 적지만 만료 복원과 판매자 0 입력이 교차하면 품절 상품이 다시 열리거나 이중 차감될 수 있다.
3. 판매자 재고 0 입력을 예약 종료까지 거부: 단순하지만 신산님의 즉시 새 구매 차단 결정과 맞지 않는다.

따라서 1안을 설계 기준으로 사용한다. 다음 번호의 migration은 기존 0009까지의 이력 뒤에 새 표·인덱스만 추가하도록 계획한다. 정확한 SQL과 공유 DB 적용 범위는 구현계획에서 검증하고 별도로 승인받는다.

## 데이터 경계와 불변식

- 제안 관계: `checkout_reservations(id, account_id, idempotency_key, status, created_at, expires_at, ended_at, end_reason)`와 `checkout_reservation_lines(reservation_id, option_id, quantity)`. 계정·옵션 FK, 품목 `(reservation_id,option_id)` 복합키, 양의 정수 수량, 계정+멱등키 유일성, 계정별 `ACTIVE` 예약 최대 1개를 부분 유일 인덱스로 보장한다. 행은 만료/해제 후에도 추적 이력으로 남긴다. 카드·PG 정보는 저장하지 않는다.
- 제안 관계: `inventory_deferred_stock_targets(id, option_id, target_on_hand=0, requested_by_account_id, requested_at, status, applied_at)`. 옵션당 `pending` 목표 최대 1개를 부분 유일 인덱스로 보장한다. 판매자가 0을 요청한 시점과 실제 0 반영 시점을 분리한다. 활성 보유 중인 옵션에만 대기 0을 만들고, 적용·대체 이력을 감사 사건과 함께 남긴다. 기존 `inventory_levels`의 컬럼 의미나 기존 행을 일괄 재작성하지 않는다.
- 현재 `inventory_levels.on_hand_quantity`는 예약분을 포함한 보유량, `sellable_quantity`는 승인된 판매 기준 수량이다. 신규 고객에게 표시·예약 가능한 수량은 `max(0, sellable_quantity - 만료 전 ACTIVE 예약 수량)`이다. 동일 옵션의 두 고객이 이 값을 동시에 소비하지 않도록 **옵션 행→재고 행을 같은 순서로 잠그고** 예약 유효성·합계를 잠금 안에서 확인한다. 다중 옵션은 옵션 ID 순으로 잠근다.
- 판매자가 예약 중 0을 입력하면 `sellable_quantity=0`을 즉시 반영해 새 구매를 닫고, `on_hand_quantity`는 적어도 활성 예약 수량만큼 유지하며 0 목표를 대기 기록에 남긴다. 마지막 예약이 만료·해제·소비되면 대기 0을 적용한다. 0이 아닌 입력이 활성 예약 수량보다 적으면 물리적으로 보전할 수 없으므로 409와 예약 수량 안내를 돌려주고 기존 재고는 보존한다. 필요한 경우 운영자가 먼저 예약을 사유와 함께 취소한다.
- 활성 예약은 보유량보다 많아질 수 없으며, 예약 종료/소비/운영자 취소/판매자 0 입력은 한 트랜잭션 안에서 재고·예약 상태·감사 이력을 함께 변경한다. 실패 시 전부 rollback한다. 예약 `ACTIVE`는 한 번만 `EXPIRED`, `RELEASED`, `CANCELLED`, 또는 향후 주문·결제 단계의 `CONSUMED`로 바뀌며 다시 활성화되지 않는다.

## 고객·판매자·운영자 흐름

1. 고객이 결제 진행을 누르면 서버는 세션 고객의 저장 장바구니만 읽는다. 빈 목록, 구버전 옵션, 판매중지·품절, 수량 초과를 거부하고 현재 공개 버전·서버 가격·배송정책으로 다시 견적한다. 클라이언트가 보내는 가격·판매자·재고·만료 시각은 신뢰하지 않는다.
2. 모든 옵션을 안정된 순서로 잠근 뒤 유효 예약 합계와 현재 판매 가능 수량을 확인하고, 같은 트랜잭션에서 15분짜리 예약·품목 행과 감사 이력을 쓴다. 만료 시각은 생성 시 DB `clock_timestamp() + interval '15 minutes'`로 고정한다. 결과에는 예약 ID, DB 만료 시각, 재확인한 견적만 반환한다. 서로 다른 고객의 마지막 1개 경합에서는 한 고객만 성공한다.
3. 고객은 요청마다 UUID 형식의 `Idempotency-Key`를 보낸다. 같은 고객의 동일 키 재시도는 기존 예약 결과를 돌려주며 **15분을 연장하지 않는다**. 종료된 키도 재활성화하지 않는다. 다른 키로 두 번째 활성 예약을 만들려면 기존 예약을 명시적으로 해제한 뒤 다시 시도해야 한다. 예약 중 장바구니 PUT/DELETE는 409로 거부하고 해제 후 수정을 안내해 조용한 재고 해제를 피한다.
4. 고객이 예약을 취소하거나 15분이 지나면 예약을 한 번만 종료한다. 조회·새 예약·주문 접수에서 만료를 선처리하고, 주기적 정리 작업도 같은 멱등 상태 전이를 사용한다. 정리 작업이 늦어도 `expires_at > DB 현재 시각`인 예약만 신규 판매 가능 수량에서 빼므로 품절 수량을 영구 점유하지 않는다. 대기 0이 있으면 종료 트랜잭션에서 이를 적용한다.
5. 고객 화면은 남은 시간을 안내하되 브라우저 시간이 만료 판정을 하지 않는다. 만료·운영자 취소 시 재견적/재시도를 요구한다. 예약 고객의 기존 보유 수량은 일반 신규 판매 가능 수량과 별도로 검증해 자기 예약 때문에 구매 불가로 표시하지 않는다.
6. 판매자가 0을 입력하면 화면에 `새 판매 중단`, `기존 예약 수량`, `예약 종료 후 보유 0 적용`을 구분한다. 운영자에게 실물 부족이 확인되면 운영자만 사유를 적어 해당 예약을 취소하고 고객에게 상태를 보여준다. 자동 이체·실발송 조치는 하지 않는다.

## 상품 변경·주문 접점

- 활성 예약이 있는 상품의 **새 개정 승인**은 409로 보류한다. 동일 이름 옵션 재고 승계는 예약 종료 뒤 기존 승인 흐름을 그대로 사용한다. 예약 중 옵션 ID를 자동 치환하거나 새 가격을 몰래 수락시키지 않는다. 운영자는 필요한 경우 사유를 적어 예약을 취소한 후 개정을 승인한다.
- **판매중지 승인**은 신규 판매를 즉시 막고 같은 트랜잭션에서 해당 상품의 활성 예약을 사유와 함께 취소한다. 이는 판매자 재고 0 입력과 달리 상품 판매 자체가 중지된 경우다.
- 배송정책·프로모션 등 금액이 예약 중 바뀌면 예약 수량은 유지하되 주문 접수 전 서버가 다시 계산하여 고객에게 새 금액 수락을 요구한다. 고객이 거부하거나 만료되면 예약을 해제한다. 발송 묶음별 주문·원 단위 할인 배분과 PG 대조는 S3.2~S4 계약에서 연결한다.
- 향후 주문·결제 소비는 동일 예약 ID를 한 번만 확정하고 `on_hand_quantity`에서 예약 수량을 차감한다. 결제 실패·기간 초과는 소비하지 않고 해제한다. 이 단위에서 주문/결제 완료 화면이나 소비 성공을 주장하지 않는다.

## 제안 공개 API·접근 제어

| 경로 | 계약 |
|---|---|
| `POST /customer/checkout/reservations` | 고객 세션·신뢰 Origin·멱등키 필수. 본문 가격/재고는 받지 않고 저장 장바구니를 예약. 성공 시 ID·서버 만료시각·현재 견적. |
| `GET /customer/checkout/reservations/:id` | 소유 고객만 상태·만료시각·품목·현재 재견적 확인. 다른 고객 ID는 정보 유출 없이 거부. |
| `DELETE /customer/checkout/reservations/:id` | 소유 고객의 활성 예약 해제. 반복 요청은 종료된 상태를 반환하고 재고를 두 번 바꾸지 않음. |
| `POST /checkout/admin/reservations/:id/cancel` | 운영자 역할·신뢰 Origin·사유 필수. 실제 배송 불능·상품 판매중지 예외를 감사에 남긴다. 판매자나 고객은 이 권한을 얻지 않는다. |

400은 형식·멱등키·취소 사유 오류, 401은 비로그인, 403은 역할/Origin 거부, 404는 존재하지 않거나 소유하지 않은 예약, 409는 품절·만료·다른 활성 예약·금액 재확인·옵션 변경, 503은 DB 미준비다. SQL 상세와 다른 고객의 예약 ID/수량은 응답하지 않는다. 위 API와 관계는 **제안**이며 이 문서 검토만으로 공개 계약·migration 적용을 허가하지 않는다.

## 검증·복구 경계

- RED→GREEN 실DB 시험: 마지막 1개를 두 고객이 동시에 예약, 동일 멱등키 반복/서로 다른 키 충돌, 15분 만료와 중복 정리, 판매자 0 입력 전후 신규 구매 차단·기존 예약 유지·종료 후 0 반영, 다른 양수 감소의 예약 수량 미만 거부, 상품 개정/판매중지, 정책 변경 재견적, 고객·판매자·운영자 권한/Origin/IDOR, 만료 이후 늦은 주문 거부를 포함한다.
- 시간 시험은 시험 소유 예약의 `expires_at`을 격리 DB에서 과거로 이동해 DB 시각 기준으로 검사한다. 실시간 15분 sleep에 의존하지 않는다. 두 고객 경합은 실제 병렬 DB 세션에서 검증한다. 로컬 무DB skip은 실DB 합격으로 세지 않는다.
- 새 관계는 우선 고유 격리 DB에서 기존 0000~0009 뒤 적용·새 DB 전체 적용·정리 시험을 한 뒤, 공유 `local-postgres/shoppingmall`의 실제 적용은 대상·SQL·기존 행·rollback 영향을 별도 확인한다. 실패 시 기존 예약/주문 이력 삭제나 DB 초기화 대신 쓰기 경로를 닫고 보정 migration으로 복구한다.
- 실제 브라우저에서는 구매자 예약 시작/남은 시간/만료·재견적, 판매자 0 입력과 운영자 취소 표시를 가상 계정으로 확인한다. QA 계정·상품·예약·감사 행과 이름 붙인 컨테이너를 실행별로 정리해 잔류 0을 확인한다. PG 실승인·Oracle 인수·200% 확대 등 아직 수행하지 않은 검증은 합격으로 표시하지 않는다.
