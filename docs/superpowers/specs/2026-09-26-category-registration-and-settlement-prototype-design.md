# 어울몰 분류·등록·정산 조회 클릭형 시안 설계

- 상태: 신산님 **서면 검토 대기** (2026-09-26). 대화에서 시안 확장 방향은 승인됐으나 이 문서·구현 계획·변경된 화면은 아직 승인되지 않았다.
- 정본과 경계: [제품 설계](../../design/DESIGN.md), [기존 클릭형 시안 설계](2026-09-26-clickable-prototype-design.md), [현 시안 안내](../../design/prototypes/README.md), [작업현황](../../../WORK_STATUS.md). 신산님 최신 직접 지시가 이 문서의 제안보다 우선한다.

## 1. 목적과 범위

관리자가 판매자와 상품의 분류를 먼저 만들고, 판매자가 분류에 맞는 상품을 등록 요청하며, 고객은 승인된 상품을 분류별로 탐색하는 절차를 **역할별 독립 클릭형 시안**에서 이해할 수 있게 한다. 관리자 정산 조회는 전체·판매자 분류·개별 판매자를 선택할 수 있고, 조회 결과와 인쇄물은 판매자별로 나뉘어야 한다.

이번 산출물은 기존 `docs/design/prototypes/`의 가상 HTML/CSS/JavaScript 시안과 자동 검사, 검토 안내다. 실제 상품·판매자 등록, DB schema, 계정/권한, 승인 서버, 사진 업로드, 결제, 정산 송금은 구현하지 않는다. 기존 어울몰 브랜드, 황금·크림 디자인과 글자 크기, 세 역할 시안의 독립성과 새로고침 초기화 규칙을 유지한다.

## 2. 정보 구조와 권한

상품 분류는 정확히 **대분류 → 소분류 → 상품**이다. 상품 하나는 한 소분류에 속하고 그 소분류의 대분류가 결정된다. 3단계 카테고리나 특정 지역 상품의 등록 제한은 두지 않는다. 분류 이름과 예시 품목은 가상 자료이며 최종 실판매 분류 체계로 확정하지 않는다.

판매자 구조는 별도로 **판매자 분류 → 판매자**다. 관리자가 자유롭게 이름을 정한 판매자 분류를 만들고, 판매자 등록 화면에서 분류 하나를 선택해 판매자를 등록한다. 분류 기준을 지역·주력 품목·발송 방식 중 하나로 고정하지 않는다. 농가와 어울몰 판매자는 모두 같은 판매자 목록의 구성원이며, 어울몰 전용 등록·판매내역·정산 조회 화면을 따로 만들지 않는다. 상품 분류와 판매자 분류는 다른 축이므로 서로 자동으로 결정되지 않는다.

관리자는 두 분류 체계의 생성과 판매자 등록을 담당한다. 판매자는 자신의 판매자 소속에서 기존 상품 소분류를 선택해 상품 등록을 요청할 수 있고 다른 판매자 상품을 등록하지 못한다. 신규 상품은 `승인 대기` 동안 고객 목록에 공개되지 않으며 관리자가 승인한 뒤 공개되는 원칙을 시연한다. 실제 권한 검증이나 역할 간 데이터 전달은 이 독립 시안에서 주장하지 않는다.

## 3. 역할별 화면 흐름

### 관리자

1. `판매자 등록`에서 판매자 분류를 추가하고, 그 분류에 속할 판매자 이름을 등록한다. 판매자 분류가 없으면 판매자 등록을 막고 안내한다. 동일 분류 안에서 같은 이름의 중복 등록도 막는다. 어울몰 판매자는 일반 판매자와 같은 형식으로 예시 등록한다.
2. `상품 분류 관리`에서 대분류를 만들고, 선택한 대분류 아래 소분류를 만든다. 대분류 없이 소분류를 만들 수 없고, 상품 등록에서 소분류가 없는 대분류는 최종 선택할 수 없다. 빈 값과 동일 부모 내 중복 이름을 거부한다.
3. `상품 승인`에서 판매자 상품 요청의 판매자, 대·소분류, 상품명, 가격·재고, 산지, 발송 방식의 제안 자료를 읽고 승인 또는 반려한다. 신규 상품의 기존 값은 `없음`으로 표시한다. 관리자 시안의 승인 상태만 바뀌며 판매자·고객 시안에는 전파되지 않는다고 밝힌다. 기존 배송 정책 승인 예시는 유지한다.

### 판매자

1. 자기 소속 판매자 이름을 확인하고 `상품 등록 요청` 화면에서 관리자가 만든 대분류·소분류를 차례로 선택한다. 상품명, 가상 가격, 초기 재고, 산지, 품목별 발송 방식의 최소 입력값을 넣어 요청한다. 사진은 자리표시/안내만 제공하고 실제 파일을 업로드하지 않는다.
2. 소분류 미선택, 빈 상품명·산지, 유효하지 않은 가격·재고, 발송 방식 미선택은 제출을 막는다. 제출한 상품은 시안 내 `승인 대기`로 표시하며 고객 공개로 표시하지 않는다. 기존 재고 감소의 즉시 반영과 재고 증가·품절 해제의 승인 대기는 유지한다.

### 고객

1. 상품 화면에 대분류와 그 아래 소분류 탐색을 둔다. 소분류 선택 시 그 아래 공개 상품만 보인다. 전체 선택에서는 공개 상품 전체를 보여 준다. 결과가 없는 분류는 빈 상태를 명확히 표시한다.
2. 기존 고추·고춧가루·양파·마늘·블루베리 예시에 소분류를 부여한다. 시안용 분류 이름은 예시일 뿐 운영 분류 확정이 아니다. 장바구니 수량·가격, 품절 차단, 발송 주문 분리, 통합 모의 결제는 기존 동작을 유지한다. 승인 대기 상품은 고객 목록에 나오지 않는다.

## 4. 정산 조회·인쇄

관리자 정산 조회 대상은 **전체 / 판매자 분류 / 개별 판매자**의 세 방식이다. 분류 조회는 해당 분류에 소속된 판매자만, 개별 조회는 해당 판매자만, 전체 조회는 어울몰 판매자를 포함한 모든 판매자를 대상으로 한다. 시작일·종료일은 발생일 기준이며 기존 5월 판매·7월 환불의 원주문 연결을 유지한다.

전체·분류 조회의 결과는 날짜순으로 판매자들을 섞은 한 표가 아니다. **판매자마다 제목, 항목별 소계, 발생 내역 표를 따로** 보여 준다. 전체 합계는 별도 요약으로만 두고 판매자 표를 합치지 않는다. 개별 조회도 같은 판매자 구획 하나를 보여 준다. 해당 범위에 판매자가 없거나 판매자의 기간 내 발생 내역이 없으면 범위에 맞는 빈 상태를 표시한다.

`조회 결과 인쇄 / PDF 저장`은 마지막으로 성공한 조회의 대상·기간·판매자별 구획을 그대로 인쇄한다. PDF 파일은 브라우저 인쇄 창에서 `PDF로 저장`을 선택하는 방식이며 직접 파일 다운로드는 없다. 필터 입력만 바꾸고 `기간 조회`를 누르지 않으면 직전 조회 결과가 인쇄된다는 점을 안내한다. 정산 완료 상태는 판매자별 개별 선택에서만 기록할 수 있고 전체·분류 조회에서 일괄 완료할 수 없다. 어울몰 판매자도 조회와 완료 상태 표시는 다른 판매자와 동일하게 취급한다. 최종 지급액 자동 결정·송금은 하지 않는다.

## 5. 시안 상태·예시 자료와 예외

기존 고객·판매자·관리자 시안은 각자 메모리 상태만 쓰고 서로 import·저장소·서버·DB로 상태를 전달하지 않는다. 세 화면의 같은 상품/판매자 이름은 **서로 연결된 실데이터가 아니라 별도의 설명용 예시**다. 관리자에서 새 분류나 판매자를 만들거나 상품을 승인해도 다른 시안 화면에 자동 반영되지 않는다. 각 화면 상단과 안내문에 이 경계를 보인다.

예시는 두 개 이상의 상품 대분류와 여러 소분류, 두 개 이상의 판매자 분류, 농가 A·농가 B·어울몰 판매자를 포함한다. 상품의 산지는 전국 어디나 가능하다. 정산 예시는 세 판매자의 발생 항목을 구분할 수 있게 하되 금액 부담 주체나 최종 지급액을 임의 계산하지 않는다. 판매자 분류 재배치·삭제, 실제 상품 이미지/옵션, 상품 다중 카테고리, 정산 데이터의 영속 보관과 과거 분류 기준은 이 시안에서 결정하지 않고 실제 제품 설계·DB 승인 단계의 별도 항목으로 둔다.

## 6. 검증과 인계 기준

- 상품 분류와 판매자 분류가 서로 섞이지 않고 각각 부모가 먼저 존재해야 하며, 중복·빈 입력이 거부되는지 모델 및 화면 연결 검사로 확인한다.
- 판매자의 등록 요청이 소분류와 자기 판매자 소속을 가지며 승인 전에는 고객 공개 상품이 되지 않는지 확인한다. 실제 권한/서버 연동 검증으로 표시하지 않는다.
- 고객의 전체/대·소분류 선택 결과가 기대 상품을 보여 주고 빈 결과를 안내하며, 기존 구매 금액·수량 검사가 회귀하지 않는지 확인한다.
- 정산 전체/판매자 분류/개별 조회가 판매자별 표와 소계를 분리하고 어울몰 판매자를 포함하는지, 집계·발생일·원주문 연결이 맞는지 확인한다. 전체·분류의 일괄 완료는 거부한다.
- 인쇄 핸들러가 현재 **조회된** 결과를 대상으로 호출되는지 자동 검사한다. 실제 브라우저 인쇄·PDF 파일·화면 크기·키보드/확대 검증은 수행했을 때만 별도 PASS로 기록한다. `file://` 브라우저 자동 조작 정책은 우회하지 않는다.
- 신산님이 수정 시안을 다시 검토·승인하기 전에는 제품 개발 착수·DB/계정/외부 연결 승인으로 간주하지 않는다. 현재 Git은 무커밋 `master`/원격 미설정이므로 최초 기준선 승인 전 이 문서를 커밋·push하지 않는다.

## 7. 추가 기능·관제 요구의 반영 경계 (신산님 검토 요청)

신산님이 제시한 기능 목록과 관제 기준을 기존 [PRD](../../PRD.md), [제품 설계](../../design/DESIGN.md), [작업계획](../../WORK_PLAN.md), [기술 방향](../../TECH_STACK_PROPOSAL.md)에 대조했다. 아래는 **실서비스 설계 보완안**이며 이 문서의 독립 클릭형 시안에 모든 기능이 구현된다는 뜻이 아니다. 기존 승인 문서의 확정 범위를 이 초안만으로 변경하지 않는다.

| 추가 항목 | 기존 범위와 필요한 보완 | 이 클릭형 시안의 처리 |
|---|---|---|
| 공통 계정·권한, 검색·필터·정렬, 반응형, 감사 로그 | 역할/소속 권한, 상품 검색·필터·정렬, 반응형, 행위자·역할·시각·사유 이력은 기존 PRD·계획에 있음. 판매자 분류/상품 소분류를 검색·필터 축에 추가하고 승인·정지·정산 완료도 감사 대상임을 상세 설계에 명시할 필요가 있음 | 분류 탐색·가상 승인 이력만 시연. 실제 로그인·검색 인덱스·서버 감사 기록은 없음 |
| 구매자 상품 상세·리뷰, 장바구니 CRUD, 주문·결제 콜백, 배송 추적 | 기본 범위에 있음. 결제수단은 카드부터 검증하고 간편결제·가상계좌는 공급자 지원 및 후속 범위 결정이 필요함. 특히 가상계좌는 입금 대기·기한 만료·중복/지연 통지 상태를 별도 설계해야 함 | 장바구니 수량·제거와 모의 결제까지만. 실결제·콜백·배송사 자동 추적은 없음 |
| 판매자 상품 등록·수정·삭제, 다중 이미지·옵션·상세 편집 | 등록 요청/관리자 승인과 다중 이미지·옵션은 기존 범위. 대표 썸네일과 상세 이미지의 용도·순서·미리보기, 상세 설명 편집과 삭제 대신 판매 중지/보존 이력 처리 기준은 상세 설계에서 보완 필요. 고객 공개에 영향을 주는 수정은 관리자 승인 전 비공개 유지 | 이번 시안은 신규 상품 등록 요청과 자리표시 이미지만; 실제 업로드·에디터·삭제 없음 |
| 판매자 주문 필터·배송 상태, 공지·정산·클레임 | 담당 주문/운송장, 정산 상태 조회, 문의·클레임은 기존 범위. 상태별 목록 필터와 클레임의 판매자 답변→관리자 최종 환불 결정을 화면 흐름으로 명시할 필요가 있음. 판매자 공지는 내부 업무 공지인지 고객 공개 공지인지 구분하고, 고객 공개라면 기존 관리자 승인 원칙을 적용해야 함 | 기존 출고 예시만 유지. 새 공지·클레임 화면은 시안 범위 밖 |
| 운영 KPI·지연 경보·운영 제어 | 기존 운영 예외 목록은 있으나 실시간 KPI 대시보드, 룰 기반 배송 지연·이상 알림, 서비스 공지·결제 점검·판매자 정지 제어는 별도 기능·권한·영향·복구 설계가 필요함. 어울몰 판매자에도 같은 판매자 규칙 적용. 정산/수수료 모니터링은 확정 지급액 계산 없이 기존 발생 항목·상태를 표시 | 현 정산 분류별 조회만 포함. 실시간 관제·강제 정지·결제 점검 스위치는 구현하지 않음 |

### 운영 지표·알람 초안

제시된 `주문 생성 실패율 < 0.5%`, `결제 승인 완료 지연 95p < 3초`, `배송 상태 갱신 지연 < 5분`, `페이지 응답시간 95p < 2.5초`는 **측정·합의 전 목표 후보**로 기록한다. 기존 PRD의 결제 성공률 95% 등은 지표의 분모와 시점이 달라 단순히 대체하지 않는다. 운영 기준 확정 전에는 주문 실패 분모와 제외 사유, 결제 지연의 시작/종료 사건과 외부 PG 대기 포함 여부, 배송 갱신의 기준 사건(판매자 입력/택배사 제공), 페이지별 대상·측정 구간·표본량을 정해야 한다. 특히 택배사 자동 상태 동기화가 초기 범위 밖인 동안 `5분`은 외부 배송 상태 도착을 보장하는 수치가 될 수 없다.

알람 후보는 결제 실패 급증, `PAID` 장기 미출고, 배송 지연(예시 24시간), API 오류율 급등이다. 임계치·관측 기간·수신자·중복 억제는 실제 운영 데이터와 인력에 맞춰 확정한다. 대응 흐름은 `경보 확인/운영 화면 → 원주문·결제·출고·API 로그 확인 → Runbook에 따른 복구 또는 승인된 롤백`으로 설계하되, 고객 거래·지속 데이터를 자동 삭제하거나 운영 환경을 무승인 전환하지 않는다. 운영자 대시보드와 Runbook의 구현·실측은 별도 단계 계획과 인수 검증 대상이다.

### 외부 연동 후보와 순서

- 결제: **토스페이먼츠**는 기존 첫 검증 후보를 유지한다. 신산님이 제시한 토스 계열/아임포트는 비교 후보로 기록하되 이 단계에서 특정 사업자 계약·요금·결제수단을 확정하지 않는다. 개발 중에는 mock 또는 제공되는 sandbox로 콜백·취소·부분 환불 계약을 검증하고 실연동 범위는 인수테스트 때 결정한다.
- 택배: CJ대한통운·우체국택배·한진 등의 API는 **후속 자동 상태 동기화 후보**다. 초기에는 판매자가 택배사·운송장을 입력하고 고객에게 상태/추적 링크를 보여 준다는 기존 설계를 유지한다. 계약·접근 권한·상태 매핑·갱신 지연 검증 후 자동 연동 범위를 정한다.
- 주소·지도: 배송지 입력의 주소 검색/표준화와 지도 표시는 서로 다른 기능이다. 카카오/네이버 지도는 후보로 기록하고, 배송지 주소 검증·우편번호·배송 불가 지역 판정의 근거를 별도 설계한다. 지도 SDK만으로 주소 표준화가 충족된다고 간주하지 않는다.
- 메시지: 기존 SMS·이메일·Expo 푸시 후보에 알림톡을 비교 후보로 추가한다. 주문 상태 저장을 우선하고 채널 발송은 재시도·중복 방지·수신 설정/실패 대체 경로를 갖춘다. 계정·계약·발신 등록·실발송 검증 범위는 인수테스트에서 결정한다.

### 역할별 전체 여정 보완안

- 구매자: `상품 탐색 → 상세(이미지 갤러리·옵션·배송/교환/환불 안내) → 장바구니 → 발송 주문 구분 확인·통합 결제 → 결제 완료/주문·배송 상태 추적 → 구매 확정 리뷰·교환/반품 요청·1:1 문의`. 이미지 갤러리와 정책 안내, 문의/클레임은 실제 제품 화면의 상세 설계 항목이다. 이 클릭형 시안에는 현재 상품 탐색·장바구니·모의 결제까지만 포함한다.
- 판매자: `자기 상품 등록 요청(다중 사진·상세 정보·미리보기) → 수정/판매 중지 요청 → 담당 주문 접수/상태별 조회 → 준비·출고·배송 정보 입력 → 담당 취소/교환/반품 요청 확인·자료 제출·답변 → 담당 매출/반품/CS 지표 조회`. 상품 기록이나 완료 주문은 단순 물리 삭제하지 않고 판매 중지·이력 보존을 기본으로 제안한다. 배송 완료는 운송장 입력만으로 임의 확정하지 않으며 실제 상태의 출처를 정한다. 판매자의 클레임 대응은 관리자 환불 최종 결정·집행 권한을 포함하지 않는다. 고객 공개를 바꾸는 상품 수정은 기존 승인 원칙을 따른다.
- 운영자(기존 `관리자` 역할): `전체 대시보드(주문·매출·장바구니/결제 이탈·CS·재고) → 배송 예외(지연·예상 지연·반송·보류) → 민감 조치 재인증 → 공지·점검·정책 변경·이상 경보 대응`. 이탈 지표는 집계 사건·분모와 개인정보 수집 범위를 정한 뒤 구현한다. 예상 지연은 근거 사건/룰 없이는 예측 정확도를 주장하지 않는다. 운영 제어의 역할·사유·시각·전후 상태·복구 이력을 남기고 고객 영향 조치를 별도 승인/공지 기준과 연결한다.

**운영자 PIN 기본값 `0000`은 채택하지 않는다.** 알려진 공통 기본 PIN은 민감 기능 보호가 되지 않는다. 기존 관리자 세션과 별개로 민감 조치 전 재인증(예: 비밀번호/2차 인증), 짧은 유효 시간, 시도 제한, 서버 권한 검사와 감사 이력을 권장한다. 재인증 방식·보호 메뉴·비상 복구 절차는 인증/권한 설계의 별도 승인 대상이며 클릭형 시안에는 실제 잠금 해제를 구현하지 않는다.

### 데이터·이벤트·관측 기술 후보

| 영역 | 이번 설계 검토안 | 도입 판단·검증 경계 |
|---|---|---|
| Cache/세션 | Redis는 상품 조회 캐시·속도 제한·세션 저장 등의 **선택 후보**. 주문 금액·재고·결제 상태의 정본은 계속 PostgreSQL/서버 검증 결과로 둔다 | 실제 부하·세션 유지/장애 복구 요구가 확인되면 도입. 캐시 무효화와 Redis 장애 시 로그인/결제 영향부터 설계. 기본 PIN이나 세션만으로 관리자 권한을 우회하지 않음 |
| 이미지·첨부 | S3 호환 객체 저장소 인터페이스는 기존 기술 방향과 일치. 상품 대표/상세 이미지·리뷰/클레임 증빙을 구분 | 공급자·비용·접근권한은 미확정. 업로드 형식/용량·비공개 증빙 접근·삭제/보존 정책을 별도 검증 |
| 이벤트 전파/작업 | 주문 생성·결제 완료·배송 갱신은 **DB에 먼저 확정**하고, 알림·집계 등 후속 처리를 DB 기반 작업/재시도로 연결하는 기존 방향 유지. 외부 메시지 큐는 확장 후보 | 중복/역순/실패 재처리와 원거래 추적이 필수. 처리량·지연·운영 부담이 DB 작업 경계를 넘는 증거가 있을 때 큐 제품과 전환 절차 결정. 큐 수신만으로 결제 완료를 확정하지 않음 |
| 검색 | 초기에는 기존 PostgreSQL 상품 검색·필터·정렬 방향. 한국어 검색 품질·카탈로그 규모에 따라 Full Text Search 설정 또는 OpenSearch 검토 | 실제 한국어 검색어·오타·동의어 품질과 응답 시간 측정 후 인덱스/엔진 결정. OpenSearch를 초기 필수 자원으로 고정하지 않음 |
| 모니터링·로그 | 주문/결제/배송 상태 사건·오류율·지연 측정 및 구조화 로그는 운영 지표의 선행 조건. Prometheus+Grafana, 로그 수집기 Loki 또는 ELK는 구현 후보 | WSL 시험 환경과 운영 환경의 보관 기간·접근권한·개인정보 마스킹·알람 수신자·운영비를 정한 뒤 선택. 대시보드 설치만으로 SLA 충족을 주장하지 않음 |

이 절의 운영 제어, 새로운 결제수단·외부 연동, SLA 수치 확정은 기존 승인 MVP에 자동 추가하지 않는다. 신산님이 보완안의 우선순위와 초기 출시 포함 여부를 검토한 뒤 PRD·제품 설계·작업계획에 반영한다.
