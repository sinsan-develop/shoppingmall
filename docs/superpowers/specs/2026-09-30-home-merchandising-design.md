# 어울몰 홈 전시·기획전 편집 설계

- 상태: **2026-09-30 서면 설계 승인**. 신산님이 이 문서 검토 요청에 `계속하자`고 답한 것을 승인으로 기록한다. 세부 구현 순서와 검증 절차는 별도 구현 계획에 따른다.
- 범위: [S2.4 작업계획](../../WORK_PLAN.md)의 홈 메뉴·기획전 카드·모두에게 같은 공통 추천 편집/공개. 기존 [홈 탐색 초안](2026-09-26-home-discovery-expansion-design.md)의 다섯 영역 중 검색·카테고리·상품 상세는 현재 구현을 유지한다.
- 기준: [제품 설계](../../design/DESIGN.md), [범위 보완안](../../design/DELIVERY_SCOPE_ADDENDUM.md), [현 작업 상태](../../../WORK_STATUS.md). 어울몰 브랜드·Flat v2·전국 산지 허용·고객/판매자/관리자 분리는 변하지 않는다.

## 1. 목적과 성공 기준

관리자는 판매 가능한 상품을 골라 홈의 추가 메뉴, 기획전, 공통 추천을 구성하고 미리본 뒤 공개한다. 고객은 검색·분류 외에도 기획전의 선택 상품 목록과 추천에서 실제 상품 상세까지 끊기지 않고 이동한다. 편집 도중 내용은 고객에게 보이지 않으며, 이미 공개한 상품이 판매중지·품절·비공개가 되면 홈과 기획전에서 즉시 제외된다. 고객별 행동 수집·개인화 추천·쿠폰 금액 적용은 이 범위 밖이다.

## 2. 검토한 방식과 채택 방향

| 방식 | 장점 | 한계 |
|---|---|---|
| 코드에 고정된 카드·메뉴 | 저장 구조가 없다 | 관리자가 바꿀 수 없고 현재 정적 기획전의 실제 상품 동선이 없다 |
| 수정 즉시 고객에게 반영 | 구현이 비교적 단순하다 | 카드·메뉴·상품 목록을 편집하는 중간 상태가 노출된다 |
| **편집본과 공개본을 분리** | 미리보기·원자적 공개·이전본 복구·이력 보존이 가능하다 | 별도 저장 구조와 관리자 API가 필요하다 |

마지막 방식을 채택한다. 한 번 공개한 구성은 불변 스냅샷으로 보관하고, 공개 포인터만 원자적으로 바꾼다. 단, 상품 가격·재고·공개 승인은 스냅샷에 복사하지 않고 기존 카탈로그의 현재 값을 읽는다.

## 3. 고객 화면 계약

1. 홈의 브랜드·검색·상품 대/소분류·판매자 탐색은 기존 기능을 유지한다. 현재 이름인 `홈`과 `제철 농산물`(`/products`)은 항상 접근 가능한 고정 기본 메뉴다. 관리자는 이 둘 외의 메뉴 이름·순서·표시 여부·연결 대상을 편집한다. 고객에게 보이는 추가 메뉴는 현재 실제로 갈 수 있는 내부 화면만 가리킨다.
2. 기획전 카드는 제목, 짧은 설명, 표시 순서, 시작·종료 시각과 선택 상품 목록을 갖는다. 카드를 누르면 `/events/{id}`의 별도 기획전 화면으로 이동한다. 그 화면은 관리자가 정한 순서의 상품만 보여 준다. 행사 제목은 전시 문구일 뿐 할인 약속이 아니다.
3. 기획전의 상품은 승인된 현재 공개 개정의 판매 가능 옵션이 하나 이상 있는 상품만 노출한다. 공개 시 선택 상품이 하나도 유효하지 않으면 거부한다. 공개 후 모두 품절·판매중지되면 홈 카드를 숨기고 기존 기획전 URL에는 종료/상품 없음 안내와 상품 전체 탐색 동선을 보여 준다. 종료 시각 이후의 카드는 숨기며 오래된 URL은 같은 안내 화면으로 연결한다.
4. 카드 이미지는 선택 상품의 승인된 공개 썸네일 중 관리자가 고른 것 한 장을 사용한다. 지정 이미지가 현재 공개 개정에서 사라지면 다른 유효 썸네일을 사용하고, 모두 없으면 Flat v2 색상의 **텍스트 카드**로 표시한다. 새 외부 이미지 URL 입력·별도 배너 업로드는 S2.4에 추가하지 않는다.
5. 공통 추천은 관리자가 선택한 중복 없는 상품 ID의 순서 목록이다. 로그인 여부와 무관하게 모두 같은 구성에서 출발하되, 실제 표시 때는 현재 판매 가능한 것만 남긴다. 추천이 0건이면 추천 영역의 명확한 빈 상태를 보여 주며 최신 상품을 몰래 `관리자 추천`이라고 부르지 않는다.
6. 홈 전시 API 실패는 해당 전시 영역에만 오류/재시도 안내를 표시한다. 검색·분류·기존 상품 조회와 뒤 단계의 장바구니/결제는 영향을 받지 않는다. 메뉴의 고정 기본 경로는 전시 저장소 오류 때도 남는다.

## 4. 관리자 화면·권한 계약

- 관리자 화면에서 추가 메뉴, 기획전의 제목/설명/기간/상품 순서/대표 이미지, 추천 상품 순서를 편집본에 저장한다. 미리보기는 고객 화면과 동일한 공개 가능성 검사 결과 및 제외 사유를 보여 주되 고객에게 편집본을 공개하지 않는다.
- `저장`은 편집본만 바꾸고 `공개`가 별도 행위다. 공개 전에 연결 대상과 상품을 서버에서 다시 검증한다. 공개 후 수정은 새 편집본에만 적용하며, 명시적인 재공개 전에는 기존 고객 화면이 바뀌지 않는다. 단, 기존 상품의 판매 가능 상태와 현재 가격·재고는 즉시 반영한다.
- 관리자 세션 역할을 서버에서 검증하고 쓰기에는 기존 신뢰 Origin 검사를 적용한다. 고객·판매자는 편집본/이력 조회·저장·공개를 할 수 없다. 관리자에게 판매자 역할도 있는 경우 판매자 화면 행위는 관리자 공개 권한으로 승격되지 않는다.
- 저장·공개·이전 공개본으로 복귀는 행위자 계정, 활성 역할, 시각, 이전/새 공개본 ID를 감사 이력에 남긴다. 두 관리자가 같은 편집본을 열었다면 버전 불일치 저장을 거부하고 새 내용을 다시 불러오게 해 덮어쓰기를 막는다.
- 이 S2.4에서는 관리자가 직접 작성한다. 판매자의 행사 제안→관리자 승인 기능은 별도 계약 없이는 만들지 않는다. 상품 자체의 판매자 제안·관리자 승인은 기존 절차를 그대로 따른다.

## 5. 저장·API 계약 — 승인된 서면 설계 범위

- `home_content_draft`: 단일 편집본의 버전 번호, JSON 구성, 수정자·시각. JSON은 타입과 크기를 서버에서 검증한다. 최초 편집본은 추가 메뉴/기획전/추천이 모두 빈 구성으로 시작한다.
- `home_content_publications`: 공개할 때 복제한 불변 구성, 공개자·시각, 고유 공개 ID. 이전본은 삭제하지 않는다.
- `home_content_current`: 단일 현재 공개 ID. 공개·복귀는 트랜잭션에서 이 포인터만 교체한다. 감사 기록은 같은 트랜잭션에 쓴다. migration은 기존 상품·주문·계정 자료를 변경하거나 삭제하지 않는다.
- 구성의 참조는 임의 URL 문자열이 아니라 `home | catalog | category(id) | seller(id) | event(id) | product(id)`의 내부 대상 종류와 ID로 저장한다. 이벤트 ID는 공개본 사이에서도 유지되는 UUID다. 기획전·추천 상품 ID는 안정적인 `products.id`를 가리키며 가격·옵션/이미지는 현재 승인된 공개 개정에서 가져온다. 추가 메뉴가 `event(id)`를 가리키면 그 ID는 같은 공개본에 있어야 하고, 기간 종료·상품 없음으로 기획전이 비활성화되면 메뉴도 숨긴다. 카테고리/판매자 메뉴는 현재 공개 판매 상품이 하나도 없을 때 숨긴다.
- 공개 조회 `GET /home/content`는 `{ menu, events, recommendations }`를, `GET /home/events/:id`는 유효한 `{ id, title, description, products }`를 반환한다. 관리자 전용 `GET /home/admin/draft`는 `{ version, payload }`를, `PUT /home/admin/draft`는 동일 구조를 입력받아 버전이 일치할 때만 새 버전으로 저장한다. `GET /home/admin/preview`는 편집본과 제외 사유를, `POST /home/admin/publish`는 `{ version }`을 입력받아 공개 ID를, `GET /home/admin/history`는 공개 이력을, `POST /home/admin/restore/:publicationId`는 지정 이전본의 복구 결과를 반환한다. 없는/종료된 기획전은 제품 목록을 꾸며내지 않고 안내 상태로 응답한다.
- 서버는 공개 시 메뉴 연결 대상의 존재, 이벤트 ID 중복, 상품 ID 중복, 상품 공개/판매 가능 상태, 기간의 `종료 > 시작`, 제목·설명 길이, 목록 수 상한을 검증한다. 추가 메뉴 이름은 1~30자, 기획전 제목은 1~80자·설명은 최대 240자다. 상한은 추가 메뉴 12개, 동시 공개 기획전 12개, 기획전당 상품 50개, 추천 상품 24개다. 시간은 DB `timestamptz`로 저장하고 관리자 입력은 한국 표준시로 안내하며 시작 포함·종료 미포함이다.
- 요청 시에는 공개본을 읽고 현재 상품 공개/판매 가능 상태와 기간을 **재검사**한다. 따라서 이미 공개한 구성도 뒤늦은 품절·판매중지·개정/이미지 변경으로 깨진 고객 링크를 노출하지 않는다. 즉시 차단 조건과 충돌하지 않도록 공개 조회 응답에 장기 캐시를 두지 않는다. 공개 조회는 인증이 필요 없지만 편집본·이력·미리보기는 관리자 전용이다.

## 6. 구현·검증 경계

- 코드 책임은 `apps/api/src/home/`의 구성 검증/공개 조회/관리자 변경, `apps/web/app/`의 홈·기획전 상세·관리자 홈 편집 화면으로 분리한다. 현재 `home-catalog.tsx`의 최신 공개 상품 표시를 관리자 편집 추천으로 교체할 때 검색·카테고리·판매자 탐색을 보존한다. 기존 API의 상품 공개·판매중지·재고 조건을 재사용하며 서로 다른 조건식을 화면마다 복제하지 않는다.
- RED→GREEN 시험: 고객/판매자의 쓰기·편집본 접근 거부, Origin/버전 충돌, 저장만으로 고객 화면 불변, 한 번에 공개·복귀, 비공개/품절/판매중지/삭제 대상 제외, 기간 전·종료 후 카드 비노출, 잘못된/외부 링크 거부, 이미지 대체, 중복 상품·빈 기획전·추천 0건, 기획전→상품 상세 동선, 홈 API 실패 격리.
- 로컬 test/typecheck/lint/build 후 동일 Git SHA를 지정 WSL checkout에 push→pull하고 개발 DB migration은 별도 승인·격리 DB 적용/복구 검증 뒤에만 진행한다. 관리자/고객 역할별 실제 브라우저에서 1920×1080·1440×900·430×844, 키보드 순서·빈 상태·실제 200% 확대를 따로 확인한다. 확대 입력이 적용되지 않으면 미검증으로 둔다.
- 새 기능의 공개 전 복구는 현재 공개 포인터를 직전 검증된 공개본으로 되돌리는 관리자 행위로 수행한다. DB migration 자체는 기존 자료를 파괴하지 않고 이전 서비스 코드와의 공존·되돌림을 격리 DB에서 확인한다. 시험 fixture와 임시 컨테이너·포트는 정확한 이름으로 정리한다.

## 7. 이번 범위가 아닌 것

쿠폰·실할인/배송비 지원·프로모션 금액 계산(S3), 판매자의 행사 제안, 광고/개인화·행동 추적, 라이브/오픈마켓, 전용 배너 이미지 업로드, 외부 URL 메뉴, 자동 상품 추천은 만들지 않는다. 기획전 전시가 할인이나 배송일을 보증하는 것처럼 쓰지 않는다. Oracle/PG/실발송/인수 검증은 별도 단계다.
