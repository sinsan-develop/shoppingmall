# S3.1 로그인 계정 장바구니 계약

상태: 신산님이 2026-10-02 선택한 **서버 저장·주문 직전 15분 예약** 방식의 첫 구현 단위. 제품 범위는 기존 `docs/design/DESIGN.md` R02~R05와 `docs/WORK_PLAN.md` S3.1을 따른다. 이 문서는 장바구니 저장·재견적 계약을 구체화하며, 주문/결제·예약 테이블의 상세 계약은 다음 단위에서 확정한다.

## 목적과 경계

- 로그인한 고객은 웹과 Android 앱에서 동일한 계정의 장바구니를 읽고 상품 옵션의 수량을 직접 입력·수정·제거한다.
- 장바구니 담기·수정은 **재고를 예약하거나 결제금액을 확정하지 않는다**. 판매 가능한지 현재 상태를 검사하지만 이후 가격·재고·정책이 바뀔 수 있다.
- 견적은 매 요청마다 현재 공개 상품 버전, 단가, 판매 가능 수량, 승인된 배송정책을 서버에서 읽는다. 고객이 보내는 가격·판매자·정책은 받지 않는다.
- 동일 장바구니의 직접 발송은 판매자별로, 어울몰 모아 발송은 하나로 묶는다. 무료배송은 각 묶음의 할인 전 상품금액으로 판단한다.
- 프로모션 금액 적용(S3.2), 주문·예약 기록과 멱등성(S3.1 후속/S3.3), PG(S4)는 이 단위에서 구현하지 않는다. 주문 직전 예약의 수명은 15분이며 장바구니 저장과 독립한다.

## 접근과 공개 API

기존 쿠키 세션의 활성 역할이 `customer`인 계정만 접근한다. 읽기는 세션 확인, 변경은 기존 신뢰 Origin 검사까지 요구한다. 타 고객 계정 ID를 URL·본문에서 받지 않고 세션의 `accountId`를 사용한다. 판매자·관리자 역할로 활성화된 세션은 고객 계정과 동일인이더라도 거부한다.

| 요청 | 동작·결과 |
|---|---|
| `GET /customer/cart` | 계정의 옵션별 수량·현재 표시 정보·구매 가능 상태. 오래된 옵션도 삭제할 수 있도록 목록에 남긴다. 빈 장바구니는 빈 목록. |
| `PUT /customer/cart/items/:optionId` + `{ "quantity": 정수 }` | 해당 옵션의 **최종 수량 설정**. 반복 요청은 수량을 누적하지 않는다. 현재 공개·판매 중이고 해당 수량의 재고가 있을 때만 저장한다. |
| `DELETE /customer/cart/items/:optionId` | 해당 고객의 항목만 제거. 이미 없는 항목도 빈 상태를 반환하는 멱등 처리. |
| `GET /customer/cart/quote` | 저장된 선택을 현재 서버 가격·정책으로 다시 견적한다. 빈 장바구니나 품절/판매중지/구버전 옵션은 결제 가능 견적을 반환하지 않는다. |

입력 오류(형식·수량·항목 100개 초과)는 400, 비로그인은 401, 활성 역할이 고객이 아니면 403, 상품/재고 변경으로 지금 담을 수 없거나 재견적이 불가능하면 409, DB 미준비는 503을 사용한다. 민감한 내부 SQL 오류나 다른 계정 정보를 응답하지 않는다. 동시 수정은 옵션별 원자적 갱신이며 다른 옵션 행은 보존한다. 같은 옵션에 대한 두 기기의 마지막 성공한 쓰기가 이긴다. 더 강한 편집 버전 충돌 해결은 현 범위에 포함하지 않는다.

## 데이터와 불변식

새 `customer_cart_items`의 기본키는 `(account_id, option_id)`이다. 두 열은 기존 계정·상품 옵션을 참조한다. `quantity`는 1 이상 1,000,000 이하 정수이며 `created_at`, `updated_at`은 서버 시각이다. 단가·상품명·판매자·배송정책·합계는 이 표에 저장하지 않는다. 한 계정의 서로 다른 옵션 수는 최대 100개다. 옵션/상품 개정의 과거 행은 현재 구조처럼 보존하여 이전 장바구니 항목을 읽고 제거할 수 있다.

목록은 기존 옵션·개정과 현재 공개본·판매중지·재고를 구분한다. 과거 옵션 또는 품절 항목은 `unavailable`로 표시하고 임의의 새 옵션으로 바꾸거나 조용히 삭제하지 않는다. `GET /customer/cart/quote`는 기존 `CheckoutQuote`를 사용하되, 현재 선택을 먼저 계정 소유 DB 행에서 읽는다. 견적 조회 자체는 장바구니 행이나 재고를 변경하지 않는다. 최종 주문 접수 때는 동일 내용을 잠금 트랜잭션에서 재검증해야 하며 이 미구현 경계를 응답·화면에서 주문 가능 완료로 표현하지 않는다.

## 화면·시험

- 고객 웹 상품 상세의 옵션·수량을 장바구니로 저장하고, 장바구니에서 수량 직접 수정/제거 및 `단가 × 수량`과 발송 묶음별 배송비를 확인한다. 빈 상태·오류·품절 변경을 별도 표시한다. 모바일 앱은 S7에서 같은 API를 사용한다.
- RED→GREEN: 가상 고객 A/B의 항목 분리, 판매자/관리자 거부, Origin 거부, 같은 옵션 PUT 반복 수량 불변, 다른 옵션 보존, 100개 경계, 0·소수·과다 수량 거부, 재고 0·판매중지·개정 후 담기/재견적 거부, 오래된 항목 제거, 2판매자+어울몰 3개 발송 묶음과 서버 금액 일치.
- WSL 지정 checkout exact SHA에서 격리 migration 적용 시험 후 `local-postgres/shoppingmall` 정식 시험을 수행한다. 가상 자료는 고유 QA ID로 seed/reset하며 계정·상품·장바구니/감사행과 임시 컨테이너/DB 잔류 0을 확인한다. 로컬 DB 없는 skip은 실DB 통과로 세지 않는다.

## 복구·후속 예약

이번 migration은 기존 테이블을 삭제/재작성하지 않고 새 관계만 추가한다. 문제 시 쓰기 route를 중단하고 기존 견적 읽기는 보존한다. 이미 저장된 장바구니 행을 임의 삭제하지 않으며 보정 migration으로 복구한다. 예약 후속 단위는 `inventory_levels`의 기존 판매자 감소·0 차단/증가 승인 의미를 먼저 지켜야 한다. 15분 보유, 만료 해제, 재고 경합·상품 개정·판매중지·판매자 재고 감소와 결제 대기 충돌을 별도 RED/실DB 계약으로 검증한다. 현재 장바구니 저장이 재고 예약이나 결제 성공의 증거가 되지 않는다.
