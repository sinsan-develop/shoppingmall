# S3.3 발송 주문·통합 결제 대상 Implementation Plan — 승인 전

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 유효한 고객 예약 하나에서 발송 주문 여러 건과 통합 결제대기 주문 한 건을 원자적으로 저장한다.

**Architecture:** 기존 서버 견적·15분 예약·쿠폰 점유를 같은 PostgreSQL transaction에서 재검사하고, 주소·상품·혜택 버전·금액을 불변 주문 스냅샷으로 기록한다. 고객에게는 결제대기만 표시하며 PG 승인/환불은 S4로 남긴다.

**Tech Stack:** 현재 저장소의 Node 24, NestJS, TypeScript, PostgreSQL/Drizzle migration, Next.js Flat v2, node:test/tsx.

**Spec:** `docs/design/S3_ORDER_CONTRACT_DRAFT.md`(신산님 검토·승인 전), `docs/design/DESIGN.md` R02·R03·R05, `docs/design/S3_PROMOTION_CONTRACT_DRAFT.md`.

## Global Constraints

- 이 계획은 API 2개·새 영속 관계 5개·0012 migration 구현 승인을 대체하지 않는다. 설계 승인 전 코드 수정 금지, 공유 개발 DB 적용은 구현과 별도 승인.
- 공개 금액은 정수 원이며 `payable=goods-discount+shipping-support`; 각 발송 무료배송은 할인 전 상품액 50,000원 기준, 기본 배송비 3,000원은 승인 정책값으로 대체될 수 있다.
- 직접 판매자마다 발송 분리, 어울몰 모아 발송은 한 묶음; 모든 고객 주문은 서버에서 본인 세션·Origin·배송지 소유를 재검사한다.
- 15분 예약·쿠폰 점유·주문 만료는 유효 기한 안에서만 처리한다. `PENDING_PAYMENT`를 `PAID`로 오인하거나 실 PG 결과로 주장하지 않는다.
- 기존 0000~0011 migration·공유 DB 행·main은 수정/초기화하지 않는다. 기존 한 작업 브랜치와 지정 WSL checkout·SSH alias를 사용한다.

## Review Focus

1. 두 탭이 같은 예약을 다른 키로 제출해도 주문이 하나만 생성되는가 — Task 3 실DB 경합 시험.
2. 서버 견적과 고객 표시 금액이 1원 달라졌을 때 주문/쿠폰 점유가 남지 않는가 — Task 3 롤백 시험.
3. 어울몰 모아 발송 안의 다른 원판매자 품목을 주문 스냅샷과 향후 정산에서 구분할 수 있는가 — Task 2 품목 시험.
4. 예약 만료와 제출·쿠폰 점유가 겹쳐도 결제대기 유령 주문이 남지 않는가 — Task 4 경합 시험.
5. 타인 배송지/주문 ID, 삭제 주소와 변조 Origin이 개인정보·주문 존재를 누설하지 않는가 — Task 5 HTTP 시험.

## Self-review·승인 게이트

Spec의 주문 그룹/혜택·주소/금액·멱등/만료·권한/화면·QA/복구를 Task 1~6에 각각 연결했다. `PendingOrderView`와 `PendingOrderSnapshot`의 필드·상태는 spec 표를 정본으로 사용하며 구현 전에 임의 확장하지 않는다. 다음 진행은 신산님의 API 2개·0012 다섯 관계 구현 승인이고, 공유 개발 DB 적용은 그 뒤 격리 증거와 함께 별도 승인받는다. 이 계획 작성만으로 위 두 게이트가 열리지는 않는다.
