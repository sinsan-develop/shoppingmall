# 어울몰 2026-10-11 설계변경 후속 개발 작업계획서

> 기준: `docs/design/DESIGN.md` 1.4 변경안의 R15·R16과 `docs/design_change.md`의 미처리 기록. 이 문서는 개발 착수나 별도 승인 경계의 자동 해제가 아니다. 실행 시 `superpowers:executing-plans` 절차에 따라 작업별 시험·검증을 기록한다.

## 목표·범위

- **목표:** 판매자 본인 신청 조회와 가입·비밀번호 복구의 동일 비동기 접수 경계를 구현·검증하고, 기존 화면 시험 자료가 승인 QA DB를 안전하게 사용하도록 준비한다.
- **기준 작업공간:** `D:\Project\shoppingmall2`의 현재 작업 브랜치. 시작 전 `D:\Project\PMO\AGENTS.md`, 이 저장소의 지침·설계·작업현황·개발환경 문서, Git 상태를 다시 대조한다. 기존 dirty·untracked 파일은 보존한다.
- **시험 경계:** 제품 코드의 로컬 자동시험과 별도 격리 PostgreSQL, 이미 사용 허용된 `WSL-server/local-postgres/shoppingmall_qa_20261010_2`의 식별·자료 보호 시험만 계획한다. 보호 `shoppingmall` DB에 가상 거래를 만들지 않는다. 개발용 발송은 `disabled`/루프백 mock만 사용한다.
- **완료 판정:** 아래 개발 작업과 각 작업의 필수 검증·정리·작업현황 기록이 실제로 끝났을 때만 이 계획의 실행 결과를 판정한다. 승인 대기 또는 환경 미충족 항목은 `UNVERIFIED`로 남기며 문서 기록 자체를 시험 통과로 바꾸지 않는다.

## 승인 필요 사항 — 개발 작업과 분리

| 번호 | 왜 승인이 필요한가 | 권고안 및 정확한 승인 범위 | 승인 전 할 수 있는 일 |
|---|---|---|---|
| A1 | `GET /auth/seller-applications`는 새 공개 API·본인 자료 계약이다. | R15의 본인 전용 필드·401/권한 거부·빈 목록 계약만 승인한다. 관리자 목록이나 타인 조회, 역할 부여는 포함하지 않는다. | 기존 신청 데이터·권한 코드 확인, 계약 시험 작성. 실제 엔드포인트 공개는 보류한다. |
| A2 | 가입·복구 전용 영속 접수 큐와 작업자는 인증 처리 구조·새 DB schema/migration을 바꾼다. | R16의 동일 접수, 최소 연락 정보, 발급 자격 사후 확인, 재시도·중복·만료·감사를 승인한다. 현재 `notification_jobs`의 계정 FK를 우회하지 않고 새 migration을 작성하되 기존 0025를 변경하지 않는다. 실제 메일 발송·관리자 권한 변경은 제외한다. | 기존 타이밍·모의 발송·권한 시험과 격리 DB용 실패 시험 작성. schema 적용과 처리 경로 변경은 보류한다. |
| A3 | 새 migration을 공유 개발 DB에 적용하면 지속 데이터 구조가 변한다. | 격리 DB 전체 시험 후 대상 DB 식별·SQL 해시·기존 행·백업과 격리 복원 가능성을 제시하여 **정확한 migration 한 건의 적용을 따로 승인**받는다. 공유 적용은 이 계획의 자동 실행 항목이 아니다. | 격리 DB 적용·시험, 공유 DB 읽기 전용 준비상태 확인. |
| A4 | 기존 화면 fixture를 고정 QA DB에서 실행하면 시험 행 생성·정리 위험이 있다. | `shoppingmall_qa_20261010_2`에 한정해 시스템 식별자와 고유 run ID, 소유권·외부 참조·불변 기록 보존·정확한 정리 조건을 통과한 자료만 허용한다. 이미 받은 전용 QA DB 사용 허가 안에서 도구를 보강하며 보호 DB 허용 범위를 늘리지 않는다. | 로컬/격리 DB에서 가드의 실패 시험 및 정리 시험. |

**승인 제안 순서:** A1·A2를 각각 판단한다. A3은 SQL·격리 시험 증거가 나온 뒤 별도로 판단한다. A4는 기존 전용 QA DB 허가의 안전 구현 범위이며, 다른 DB·새 권한이 필요해지면 진행하지 않고 정확한 대상과 영향부터 다시 보고한다. 어떤 권고안도 이 문서만으로 승인된 것으로 간주하지 않는다.

## 개발 작업 — 수행 가능한 코드·검증만

### Stage 1. 기준선과 안전한 시험 준비

1. 현재 브랜치·HEAD·dirty 파일 소유를 기록하고 `apps/api/migrations/`의 최신 번호·적용 가드를 확인한다. 설계서와 이전 작업계획서는 수정하지 않는다.
2. `apps/api/src/auth/{controller,seller-applications,onboarding,password-recovery,delivery}.ts`, `apps/api/src/db/schema.ts`, `apps/web/app/signup/page.tsx`, `apps/web/app/forgot-password/page.tsx`, 관련 시험을 대조한다. 실제 `.env` 값·토큰·시험 암호는 출력·기록하지 않는다.
3. `apps/api/test/auth-seller-applications-db.test.mjs`, `auth-onboarding-http-db.test.mjs`, `auth-password-reset-db.test.mjs`, `auth-timing-baseline-db.test.mjs`의 현행 결과와 DB 미연결로 건너뛴 시험을 구분해 기록한다. 격리 자원은 정확한 이름·수명·정리 방법을 먼저 작업현황에 기록한다.

### Stage 2. R15 본인 신청 조회 — A1 승인 후

1. 위 판매자 신청 DB 시험에 `신청 없음→빈 목록`, 신청자 본인 `pending/rejected/approved`, 재로그인 후 동일 상태, 비로그인 거부, 타 계정 차단, 응답에 심사자 ID·타인 자료 없음의 실패 시험을 먼저 추가한다.
2. `apps/api/src/auth/seller-applications.ts`에 세션 `account_id`로만 조회하는 함수를 추가하고 `apps/api/src/auth/controller.ts`에 `GET /auth/seller-applications`를 연결한다. 응답 필드는 DESIGN R15만 사용한다. 조회는 INSERT/UPDATE·역할 부여를 하지 않는다.
3. 판매자 신청 화면의 실제 경로를 코드에서 확인해 본인 상태·반려 사유·빈 상태·오류를 표시한다. 기존 관리자 심사 화면과 승인 동작은 바꾸지 않는다.
4. 동일 시험 재실행, HTTP 401/본인/타인 경계, QA 계정의 새로고침·재로그인, 변경 전후 권한 회귀를 확인한다. 브라우저 시험을 못 하면 그 항목만 `UNVERIFIED`로 적고 API 통과로 대신하지 않는다.

### Stage 3. R16 동일 비동기 접수 — A2 승인 후

1. 먼저 기존·미등록 이메일의 가입/복구에서 동일 `{status:'accepted'}`와 공개 오류 형식, 응답 전 계정별 링크 발급이 없다는 실패 시험을 작성한다. 이메일 형식·남용 제한은 접수 전에 유지한다.
2. 최신 migration 번호 확인 후 **새** 인증 접수 큐 migration과 `schema.ts`를 작성한다. 최소 연락 정보·목적·상태·시각만 저장하고, 원문 비밀번호·설정/재설정 토큰·공급자 비밀은 저장하지 않는다. 기존 `notification_jobs`와 0025는 수정하지 않는다.
3. `onboarding.ts`·`password-recovery.ts`의 공개 경로를 공통 접수 함수로 연결한다. HTTP 응답 전에는 계정 존재·역할·토큰 발급·모의 발송으로 분기하지 않는다. 작업자가 접수 후 적격성·기존 발급 제한을 확인하고, 미등록 복구·중복 가입은 안전 종료한다. 관리자 역할·세션을 생성하지 않는다.
4. 작업자 실패/재시도/중복 접수/만료/경합/감사 기록 시험을 격리 DB에서 실행한다. 개발 모의 발송만 검증하고 외부 SMTP 호출이 없는지 확인한다. 작업자 재시작 뒤 미처리 건 회복과 접수·처리 결과의 비밀값 비노출을 시험한다.
5. 등록/미등록을 교차 순서로 반복 측정해 응답 내용과 처리시간 분포를 함께 기록한다. 이전 4회 표본은 기준 관찰치일 뿐 합격 기준이 아니다. 사전에 표본 수·허용 차이·환경을 시험에 명시하고 실패 시 원인을 조사한다. 로컬·격리 결과를 운영 환경의 추측 방어 증명으로 과장하지 않는다.

### Stage 4. 승인 QA DB용 화면 시험 자료 보호 — A4 범위

1. `apps/api/scripts/qa-{refund,support,fulfillment}-ui-fixture.ts`와 `qa-s6-c2-browser-fixture.ts`의 DB 이름·system ID·migration·reset 전제 및 대응 안전 시험을 각각 확인한다.
2. 승인 QA DB만 선택하는 명시적 모드를 각 도구에 추가한다. 실제 DB 이름과 PostgreSQL system ID가 계획값과 다르면 seed/reset 모두 변경 없이 거부한다. 보호 `shoppingmall` 허용 분기를 넓히거나 과거 전용 DB를 억지 생성하지 않는다.
3. 고유 run ID의 가상 계정·상품·주문만 생성하고 삭제 전 소유권·타 계정 참조·불변 정산/환불 사건을 검사한다. 삭제할 수 없는 불변 사건은 보존·식별하고 무단 SQL 삭제를 하지 않는다. 일부 생성 실패와 재실행에서도 타 자료를 지우지 않는 시험을 먼저 RED→GREEN으로 만든다.
4. 격리 DB에서 안전 시험을 통과한 뒤 자원 여유가 확인되는 경우에만 승인 QA DB에서 **한 fixture씩** seed→해당 화면 HTTP/브라우저 부분 시험→정확한 reset 또는 보존 판정→잔류 확인을 한다. 호스트가 바쁘거나 화면 도구가 없으면 fixture 코드·격리 시험까지만 증거로 기록한다. 전체 18화면·30분 부하 합격으로 확대하지 않는다.

### Stage 5. 회귀·검토·정리

1. 각 Stage의 대상 시험에서 0 fail을 확인하고 루트 `pnpm test`, `pnpm typecheck`, `pnpm lint`, `pnpm build`를 **순차** 실행한다. DB 의존 시험의 skip 수와 이유를 분리 보고한다. 실패·예상 밖 동작은 원인 분석 후 같은 범위에서 보정하고 다시 검증한다.
2. 변경 diff에서 권한 누출, 응답 전 계정 분기, 비밀값 저장, 공유 DB 시험 우회, 정상 가입/복구 회귀를 검토한다. 중요한 미해결 결함은 통과로 표시하지 않는다.
3. 격리 DB·시험 계정·프로세스·임시파일·브라우저 탭은 정확한 소유 대상을 확인해 정리하고 잔류 여부를 기록한다. 불변 기록은 보존 위치와 재개 조건을 남긴다. `WORK_STATUS.md`에 branch/HEAD·변경 파일·시험·skip·오류 횟수·미검증·다음 조치를 누적한다.
4. PR이 필요한 경우 목적·영향·검증·미검증·복구를 기록한다. 승인된 범위를 벗어난 DB 적용·외부 발송·배포는 수행하지 않는다. 계획의 실제 검증을 마친 후에만 결과와 남은 경계를 보고한다.

## 의도적으로 실행 계획에서 제외한 항목

- 현재 저장소/환경에 없는 SeaweedFS/S3 버전 계약과 상품 이미지 이관, PostgreSQL 7일 PITR·14개 백업·DB+이미지 동일 시점 복원. `archive_mode=off` 확인은 복구 기능의 검증이 아니다.
- 공유 WSL의 100동시 사용자·30분 부하와 전체 18화면 정식 통합. 현재 호스트 자원·fixture 경계로 실행 조건이 확인되지 않았다. 1사용자 smoke와 부분 화면 시험만 그 범위대로 표시한다.
- 신산님 소유 Chrome/Edge 창의 네이티브 200% 조작, 실제 이메일·문자 수신, 정식 관리자 소유 확인·계정 발급, PG·Oracle 배포·사용자 인수. viewport/CSS 시험이나 모의 발송을 이 항목의 통과로 바꾸지 않는다.
- 위 제외 항목의 계약·환경·사용자 조치가 정해지면 **후속 설계·계획·승인**으로 별도 추진한다. 이번 계획을 끝내기 위해 임의 우회하거나 거짓 완료 처리하지 않는다.

## 실행 순서와 중단 경계

`Stage 1 → A1/A2 판정 → Stage 2/3(각 승인된 것만) → Stage 4 → Stage 5`. A1 또는 A2가 아직 승인되지 않아도 Stage 1·4의 독립 작업은 진행한다. 승인·자원·접근 문제로 특정 항목이 막히면 `docs/design_change.md`에 판정·영향·수행 조치·재개 조건을 기록하고 다른 승인된 작업을 계속한다. 모든 결과에서 실제 코드/DB/브라우저 증거와 미검증 항목을 분리한다.
