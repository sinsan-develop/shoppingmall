# S6 완료 금액 고정·늦은 항목 분리 설계 제안

- 상태: **검토·별도 승인 대기**. 신산님은 2026-10-09에 “완료 당시 금액 고정·늦은 항목 별도 표시”라는 업무 정책을 선택했다. 아래 DB 구조·공개 API 변경과 공유 개발 DB 적용은 그 선택만으로 승인된 것으로 취급하지 않는다.
- 기준: `docs/design/DESIGN.md` R09, `docs/WORK_PLAN.md` S6, `docs/S6_SETTLEMENT_CONTRACT_PROPOSAL.md`의 불변 발생 장부·개별 완료·역할 범위. 자동 지급액 결정·송금은 계속 제외한다.

## 목적과 완료 의미

관리자가 판매자 A의 5월 기간을 완료한 뒤, 5월 발생일로 수수료가 늦게 등록돼도 **A의 5월 완료 당시 항목별 금액과 포함 원거래 목록은 바뀌지 않아야 한다**. 늦은 항목은 원발생일·기록일·원주문 근거를 보존해 별도로 조회·인쇄한다. 5월 판매의 7월 실제 환불은 기존 계약대로 7월 환불 발생 기록이며 5월 완료 금액에 포함하지 않는다. B 및 어울몰 판매자는 각각 독립 처리한다.

“완료 금액”은 매출·수수료·배송비·할인·지원·환불 등 **항목별 발생액의 고정된 내역**이다. 수수료나 환불의 농가·어울몰 간 부담, 최종 지급액과 이체 여부를 자동 계산하는 뜻이 아니다.

## 대안과 선택

1. **권장 — 포함 사건 ID를 고정:** 완료 기간과 그 시점에 조회 가능한 발생 장부 행의 연결을 불변으로 저장한다. 과거 합계는 연결된 행만 합산하며, 같은 발생 기간에 나중에 생긴 행은 미연결 “추가 발생”으로 분리한다. 금액뿐 아니라 원거래 구성까지 재현된다. 연결 테이블·마이그레이션이 필요하다.
2. **합계 JSON만 저장:** 완료 시 항목별 금액만 복사한다. 테이블은 작지만 합계의 구성 원거래를 정확히 증명하기 어렵고, 완료와 동시 진행한 결제/환불 사건을 늦은 항목으로 구분할 근거가 약하다. 이 사업의 근거 주문·상품 추적 요구에 맞지 않는다.
3. **기록 시각 기준 재계산:** `recorded_at <= completed_at`만 다시 조회한다. 스키마 변경은 없지만 완료 당시 미커밋 거래가 나중에 커밋되면 과거 금액이 변할 수 있으므로 고정 보장이 아니다.

## 권장 데이터·거래 계약

- 새 `0021_s6_completed_event_links.sql`은 `seller_settlement_period_event_links(period_id,event_id)` 연결 테이블과 인덱스/무결성 제약을 추가한다. `(period_id,event_id)` 중복 및 한 장부 사건이 둘 이상의 완료 기간에 포함되는 것을 막고, 판매자·발생일이 해당 완료 기간과 일치하는지 DB에서 검증한다. 연결 행은 UPDATE/DELETE 금지다. 기존 `0020_s6_settlement.sql`은 수정하지 않는다.
- 관리자 개별 완료 요청은 **한 DB 트랜잭션**에서 권한·판매자·기간을 검증하고 기존 `seller_settlement_periods`에 한 행을 추가한 뒤, 그 트랜잭션에서 보이는 해당 판매자·서울 기준 기간의 `settlement_events.id`를 모두 연결한다. 실패 시 완료 행과 연결 행을 함께 롤백한다. 같은 판매자의 기간 겹침은 기존 DB 배제 제약으로 거부하고, 다른 판매자는 독립이다.
- 완료 이력의 항목별 금액은 연결된 불변 장부 사건의 합계로 산출한다. 사건 0건인 완료도 0원으로 보존한다. 완료 뒤 같은 기간에 기록된 사건은 연결되지 않으므로 완료 금액에 추가되지 않는다. 사건과 연결이 모두 불변이므로 조회 시점·동시 커밋 순서가 완료 당시 포함 목록을 바꾸지 못한다.
- 0021 적용 전에 영속 완료 행이 있다면 원래 포함 사건을 사후 재구성할 수 없다. migration은 이를 **명시적으로 거부**하고, 식별된 QA 자료의 승인된 정리 또는 별도 복구 절차 후 다시 적용한다. 기존 완료 행을 현재 장부로 조용히 소급 채우지 않는다.

## 조회·화면 계약

- 기존 관리자·판매자 기간 조회의 판매자 구획/`totals`는 완료 기간에 **포함된 사건과 미완료 기간의 사건**만 합산한다. 완료 기간에 속하지만 연결되지 않은 사건은 새 `lateGroups`·`lateTotals`로 별도 반환·표시한다. 따라서 이미 완료한 기간의 주 합계는 늦은 입력으로 바뀌지 않는다.
- `completions[]`에 해당 완료 기간의 항목별 `frozenTotals`를 더한다. 이 금액은 연결 사건에서만 계산하고, 완료 기간과 조회 기간이 부분 겹쳐도 완료 기간 전체의 고정 합계임을 표시한다. 관리자 분류/개별 필터, 판매자 본인 범위, 전체 판매자별 분리는 기존 역할 계약을 유지한다.
- 화면·인쇄/PDF는 “완료 당시 항목별 금액”과 “완료 후 추가 발생(원발생일·기록일·원주문·사유)”을 서로 다른 구획으로 보인다. 추가 발생액을 최종 지급액에 자동 가감하거나 과거 완료 상태를 재개하지 않는다.
- 관리자 수수료 수동 입력은 별도 `POST /admin/settlement/commissions`를 제안한다. 관리자 세션·Origin 검증 뒤 판매자, 양의 원화 정수 금액, 실제 발생 시각, 1~500자 근거, 요청 UUID를 받아 `source_event_kind='manual_commission'`의 불변 장부 행을 만든다. 요청 UUID 재시도는 중복 사건을 만들지 않는다. 이미 완료한 발생 기간을 지정하면 그 완료 금액은 그대로 두고 추가 발생으로 보인다. 판매자는 입력·완료 권한 없이 자기 자료만 읽는다. 실제 수수료율·부담 주체는 입력하지 않고 자동 추론하지 않는다.

## 시험·적용·복구 경계

- 시험 우선: 5월 판매·완료 후 같은 5월 발생일의 수수료 입력 → 완료 합계/포함 원거래 불변·추가 발생 별도 노출; 7월 환불 → 7월 발생/5월 원주문 링크; 사건 0건 완료; A/B/어울몰 독립; 동시 결제/완료와 완료 재시도; 관리자 전용 입력·판매자 IDOR 거부; 전체/분류/개별/인쇄 금액 일치.
- 로컬 RED→GREEN·전체 test/typecheck/lint/build 후 격리 PostgreSQL 15에 0020→0021 적용·실제 API/DB/Chromium/PDF를 확인한다. 공유 `local-postgres/shoppingmall`에는 **별도 환경 적용 승인 전** migration·QA 행을 쓰지 않는다. 정식 WSL 통합은 정확 Git SHA, 공유 DB migration/QA entity, 실제 브라우저·원주문·인쇄 대조 및 식별 QA 자료 정리를 별도로 기록한다.
- 문제가 생기면 제품 코드를 이전 검증 commit으로 되돌리는 PR로 복구한다. 이미 생성된 완료/연결 장부를 임의 삭제하거나 0021을 역적용하지 않는다. 영속 DB 복구는 백업·영향·신산님 승인 절차를 따르며, 새 연결 테이블은 보존한다.

## 필요한 정확한 승인

신산님께 요청할 범위는 위의 **사건 ID 연결 방식**, 신규 0021 schema/migration, 관리자 수수료 입력 API와 조회 응답 필드(`lateGroups`, `lateTotals`, `completions[].frozenTotals`) 변경이다. 승인을 받아도 공유 개발 DB 실제 적용과 Oracle/운영 배포는 별도 gate다.
