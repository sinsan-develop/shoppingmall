# 어울몰 실서비스 개발 작업계획서

> 구현 담당자는 승인 후 단계별 RED→GREEN→로컬·WSL 통합검증을 수행한다. 이 문서 작성은 제품 구현·Git 초기화·DB 변경·외부 계약·배포 승인이 아니다.

**목표:** 승인된 어울몰 MVP를 고객·판매자·관리자가 시험 계정으로 실제 구매·출고·환불·정산 자료까지 검증할 수 있게 개발한다.

**구조:** 고객/판매자/관리자 웹은 Next.js 한 앱, 고객 모바일은 Expo 앱, 업무 규칙은 NestJS 단일 API에 둔다. PostgreSQL이 주문·재고·결제 이벤트의 정본이며 웹·앱은 API 계약을 공유한다. 외부 공급자는 mock/sandbox 경계를 두고 실연동 미검증을 구분한다.

**기술:** TypeScript, Next.js/React, Expo/React Native, NestJS, PostgreSQL/Drizzle. Better Auth·토스페이먼츠·SENS·Oracle Object Storage 등은 검증 후보이지 최종 계약·공급자 확정이 아니다.

**설계 기준:** [승인된 DESIGN 1.0](design/DESIGN.md), [승인된 PRD 범위](PRD.md), [승인된 기술 방향](TECH_STACK_PROPOSAL.md). 문서 승인과 별개로 화면 시안·개발환경 준비 판정 및 단계별 별도 승인 경계를 충족해야 한다.

## 1. 상태·담당·착수 게이트

- 상태: 신산님 승인 / 작성·승인 2026-09-26 / 작성자 어울 / 승인자 신산님 / 실제 Stage 시작 0건.
- 단일 writer: 같은 기능·파일에는 한 writer. 각 Stage의 담당·branch·HEAD·시험 증거는 시작·종료 시 이 문서와 `WORK_STATUS.md`에 기록한다.
- 현재 로컬 문서 작업공간 `D:\Project\shoppingmall2`에는 2026-09-26 초기 `main` root commit이 있고, 지정 `sinsan-develop/shoppingmall`의 `origin/main`과 원격 HEAD에서 확인했다. WSL `~/deploy/shopping` checkout은 아직 없다. 별개 `.github` 자동화 두 파일은 로컬 미추적 보존 중이다. 기존 `D:\Project\shoppingmall`는 참고 자료이며 신규 저장소로 바꾸지 않는다.
- 착수 전 필요: 현행 요구에 맞춘 정적/클릭형 화면 시안 검토·승인 또는 명시적 생략 결정, 코드 정본 저장소·`origin/main` 기준선·격리 branch/worktree, 로컬/WSL 공통 포트·QA 자원·Secret 참조 위치, 환경 게이트 판정. 준비는 [개발환경 문서](DEVELOPMENT_ENVIRONMENT.md)에 실제 확인 결과로 기록한다.
- 데이터 schema/migration, 인증·권한·Secret, 외부 비용·계약, Oracle 배포와 운영 전환 등 별도 승인 경계를 통과하지 않은 작업은 해당 Stage에서 실행하지 않는다. 승인 안 된 부분과 독립적인 문서·테스트 설계는 계속할 수 있다.
- 배포·인수·운영 설치는 **이 개발 작업계획의 Stage가 아니다**. 개발 검증 후 별도 설치·배포 계획과 신산님 승인으로 진행한다.

## 2. 파일·책임 지도(계획안)

| 위치 | 책임 |
|---|---|
| `apps/web/` | 고객·판매자·관리자 Next.js 화면과 웹 UI 시험 |
| `apps/mobile/` | 고객 Expo 앱과 앱 화면·흐름 시험 |
| `apps/api/src/modules/auth/` | 계정·세션·역할·판매자 소속 검증 |
| `apps/api/src/modules/catalog/`, `inventory/`, `approval/` | 상품·옵션·사진, 재고·예약, 판매자 제안·관리자 승인 |
| `apps/api/src/modules/checkout/`, `orders/`, `payments/` | 금액 견적·발송 주문 분리, 주문 상태, PG 경계·환불 |
| `apps/api/src/modules/fulfillment/`, `support/`, `notifications/` | 출고·운송장, 문의·리뷰·클레임, 알림 작업·재시도 |
| `apps/api/src/modules/settlement/` | 발생일 기준 농가별 항목 자료·기간별 완료 |
| `packages/contracts/`, `packages/design-tokens/`, `packages/test-fixtures/` | API 계약·공유 타입, 시각 토큰, 식별 가능한 QA 자료 |
| `apps/api/test/`, `apps/web/e2e/`, `apps/mobile/test/`, `docs/` | 계층별 자동·실제 검증, 사용자·운영자 문서 |

파일 구조는 구현 시작 전에 기존 코드가 없음을 다시 확인하고 DESIGN 승인 내용과 대조한다. 공개 계약·schema·권한 세부는 각 Stage의 별도 승인 대상이다. 예상 파일 경로를 실제 존재 또는 이미 승인된 API 이름으로 오인하지 않는다.

## 3. 전체 Stage 지도

`S1 계정·권한·기반 → S2 상품·재고·승인 → S3 견적·장바구니·주문 → S4 결제·취소·환불 → S5 출고·문의·알림 → S6 농가 정산 → S7 모바일 앱 → S8 전체 회귀·문서·개발 완료 판정`

S2 상품 조회 화면은 S1 웹 기반에 의존한다. S3는 S2의 판매 가능 재고와 정책에, S4는 S3의 주문·견적에, S6는 S4의 매출·환불과 S5의 발송 사건에 의존한다. S7은 안정된 S1~S5 API를 사용한다. 각 Stage는 독립 검증 가능한 기능 묶음이며 Stage별 1개 PR을 기본으로 하되 실제 크기·검증/rollback 경계가 과도하면 구현 전에 분할 승인을 받는다.

## 4. 공통 RED/GREEN·검증·검토 규칙

- 각 Stage는 누락/실패를 재현하는 시험을 먼저 기록하고 실패를 확인한 뒤 최소 구현과 통과를 증명한다. 구현 파일·테스트 이름·명령은 해당 Stage 착수 시 실제 생성 구조와 승인된 계약을 기준으로 이 계획에 고정하고, 결과를 `WORK_STATUS.md`에 누적한다.
- 필수 검사: 변경 범위 unit, API/DB 계약, typecheck, lint, build, 브라우저 실제 흐름·viewport·키보드/접근성, 필요한 앱 개발 빌드. fixture PASS는 실 PG·앱 푸시·Oracle 배포 PASS가 아니다.
- 검토 우선 실패 조건 5개: (1) 타 농가 주문 ID 조회/수정 허용→S1·S2 권한 시험, (2) 동시에 마지막 재고 구매→S3 DB 경쟁 시험, (3) 중복·역순 PG 이벤트로 중복 주문/환불→S4 사건 시험, (4) 부분 취소 후 배송비 재청구 또는 할인 합계 오차→S3·S4 금액 시험, (5) 늦은 환불을 과거 완료 정산에 소급→S6 기간 시험.
- 각 Stage PR에는 목적·영향·변경·시험·미검증·rollback을 적는다. 일반 내부 Stage 병합 가능 범위와 예외 승인은 사용자 전역 지시·PMO 지침을 따른다. 사용자 인수 대상은 정확한 PR 후보로 별도 Oracle staging 승인 후 인수, 신산님 승인 후 병합한다.
