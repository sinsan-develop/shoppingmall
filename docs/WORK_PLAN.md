# 어울몰 실서비스 개발 작업계획서

> 구현 담당자는 승인 후 단계별 RED→GREEN→로컬·WSL 통합검증을 수행한다. 이 문서 작성은 제품 구현·Git 초기화·DB 변경·외부 계약·배포 승인이 아니다.

**목표:** 승인된 어울몰 MVP를 고객·판매자·관리자가 시험 계정으로 실제 구매·출고·환불·정산 자료까지 검증할 수 있게 개발한다.

**구조:** 고객/판매자/관리자 웹은 Next.js 한 앱, 고객 모바일은 Expo 앱, 업무 규칙은 NestJS 단일 API에 둔다. PostgreSQL이 주문·재고·결제 이벤트의 정본이며 웹·앱은 API 계약을 공유한다. 외부 공급자는 mock/sandbox 경계를 두고 실연동 미검증을 구분한다.

**기술:** TypeScript, Next.js/React, Expo/React Native, NestJS, PostgreSQL/Drizzle. Better Auth·토스페이먼츠·SENS·Oracle Object Storage 등은 검증 후보이지 최종 계약·공급자 확정이 아니다.

**설계 기준:** [승인된 DESIGN 1.0](design/DESIGN.md), [승인된 PRD 범위](PRD.md), [승인된 기술 방향](TECH_STACK_PROPOSAL.md), [범위 보완안](design/DELIVERY_SCOPE_ADDENDUM.md). 신산님은 이 상세 계획에 따른 전체 구축을 직접 지시했다. 외부 서비스 가입·실연동은 구축 후 일괄 처리하며, 별도 승인 경계는 유지한다. 개발 뒤의 설치·인수는 [별도 작업계획](DEPLOYMENT_UAT_PLAN.md)을 따른다.

## 3. 전체 Stage 지도

`S0 최신 설계·시안/환경 gate → S1 계정·권한·기반 → S2 분류·상품·재고·승인/홈 → S3 프로모션·견적·장바구니·주문 → S4 결제·취소·환불 → S5 출고·문의·알림/운영 예외 → S6 판매자별 정산 → S7 앱 아이콘·Android 앱 → S8 전체 회귀·문서·개발 완료 판정 → 별도 U0~U4 인수`

S2 상품 조회 화면은 S1 웹 기반에 의존한다. S3는 S2의 판매 가능 재고와 정책에, S4는 S3의 주문·견적에, S6는 S4의 매출·환불과 S5의 발송 사건에 의존한다. S7은 안정된 S1~S5 API를 사용한다. 각 Stage는 독립 검증 가능한 기능 묶음이며 Stage별 1개 PR을 기본으로 하되 실제 크기·검증/rollback 경계가 과도하면 구현 전에 분할 승인을 받는다.

### S0 — 설계·시안·환경 준비 판정(제품 기능 구현 전)

- 입력: `origin/main` 최신 상태, 승인된 DESIGN/PRD/기술 방향, 신산님 최신 직접 결정, Flat v2 branch, PMO/프로젝트 지침, `DEVELOPMENT_ENVIRONMENT.md`. 담당은 어울; 신산님은 범위·별도 승인 경계만 결정한다.
- [ ] `origin/main`·현재 checkout·원격 URL·dirty 파일 소유자·기존 worktree/PR·자동화 효과를 읽기 전용으로 조사한다. Flat v2 로컬 정적 시안의 실제 브라우저 QA는 신산님의 직접 지시에 따라 이 게이트에서 제외한다. 실제 제품 화면의 1920×1080/1440×900/430×844·키보드·인쇄는 해당 Stage에서 검증한다. 200% 확대는 2026-10-01 직접 결정에 따라 UAT-03으로 이월하며 그전에는 미검증으로 기록한다. 선행 브랜치의 문서 이력은 보존하며 현재 `main`을 덮지 않는다.
- [ ] 상품/판매자 분류, 홈 다섯 영역, 실제 금액 프로모션, 관제 범위, Android 아이콘·에뮬레이터/실기기, iOS 후속, 시험 정책을 `DELIVERY_SCOPE_ADDENDUM.md`와 추적표로 승인받는다. 충돌하는 DESIGN 1.0 항목은 명시적 설계 변경 승인으로 처리하고 계획 승인만으로 계약을 바꾸지 않는다.
- [ ] Windows 로컬·`WSL-server`·GitHub 접속/포트 점유·기존 서비스 영향·정확한 `local-postgres`의 `shoppingmall` DB·WSL `/home/daon/deploy/shopping` 부재/생성 경계·QA 계정/데이터 수명·Secret 저장 위치(값 제외)를 확인한다. WSL checkout 생성/DB 계정·schema 변경은 해당 승인을 받아 실행한다.
- [ ] 반복 가능한 명령표(설치, test, typecheck, lint, build, DB migration dry-run, seed, WSL pull/exact SHA, 브라우저/E2E)를 실제 package scripts가 생기면 고정한다. 특정 명령/포트/이미지 이름을 지금 존재하는 것으로 가장하지 않는다.
- 종료 증거: 승인된 범위 보완안/환경 판정, 시안 자체 QA의 명시적 제외와 실제 제품 QA의 후속 Stage 배정, 최신 Git 기준선·선행 PR 상태, 테스트 자료·Secret/자원 소유·rollback 방법, 승인 게이트 목록. DB·인증·Secret 등 별도 승인 전에는 그 영향을 받는 코드를 활성화하지 않고, 독립적인 무상태 기반·시험은 계속한다.

## 4. 공통 RED/GREEN·검증·검토 규칙

- 각 Stage는 누락/실패를 재현하는 시험을 먼저 기록하고 실패를 확인한 뒤 최소 구현과 통과를 증명한다. 구현 파일·테스트 이름·명령은 해당 Stage 착수 시 실제 생성 구조와 승인된 계약을 기준으로 이 계획에 고정하고, 결과를 `WORK_STATUS.md`에 누적한다.
- 필수 검사: 변경 범위 unit, API/DB 계약, typecheck, lint, build, 브라우저 실제 흐름·viewport·키보드/접근성, 필요한 앱 개발 빌드. fixture PASS는 실 PG·앱 푸시·Oracle 배포 PASS가 아니다.
- 검토 우선 실패 조건 5개: (1) 타 농가 주문 ID 조회/수정 허용→S1·S2 권한 시험, (2) 동시에 마지막 재고 구매→S3 DB 경쟁 시험, (3) 중복·역순 PG 이벤트로 중복 주문/환불→S4 사건 시험, (4) 부분 취소 후 배송비 재청구 또는 할인 합계 오차→S3·S4 금액 시험, (5) 늦은 환불을 과거 완료 정산에 소급→S6 기간 시험.
- 각 Stage PR에는 목적·영향·변경·시험·미검증·rollback을 적는다. 일반 내부 Stage 병합 가능 범위와 예외 승인은 사용자 전역 지시·PMO 지침을 따른다. 사용자 인수 대상은 정확한 PR 후보로 별도 Oracle staging 승인 후 인수, 신산님 승인 후 병합한다.

- 출고 후 환불/반송비 법률 검토 전에는 잠정 정책을 실서비스 기본값으로 확정하지 않는다. 개발 시험은 사유별 처리·변경 가능한 정책과 증빙으로 수행한다.

## 7. 실행·검증 기록의 표준과 승인 패킷

1. 각 Task 시작 전 `WORK_STATUS.md`에 Stage/Task, 담당 writer, branch·full HEAD, 승인된 계약·선행 증거, 수정 예상 파일, DB/Secret/비용 영향, 사전 QA 자원·rollback을 기록한다. 실패는 같은 근본 원인 연속 횟수·조치/미검증까지 누적한다.
2. Task 완료 때 RED 확인 기록, GREEN 명령/종료 코드·테스트 수, typecheck/lint/build, API/DB/browser/device 결과, screenshot/log ID(개인정보 마스킹), WSL 정확한 SHA, 변경 파일·실행 후 자원 정리와 미검증을 적는다. DB/외부 공급자/기기는 각각 독립 증거다.
3. 각 Stage PR은 목적·승인 요구사항 ID·파일/데이터/API 변경·화면 영향·적용/복귀 방법·시험/미검증·잔류 자원·Critical/Important finding을 담는다. 필수 gate skip 또는 미해결 finding이 있으면 자동 병합하지 않는다. `main`의 승인된 정본·worktree/원격 복구 ref를 재확인한 뒤 다음 Stage로 간다.
4. **별도 신산님 승인 요청 패킷**: (a) 제품 범위/공개 계약 변경, (b) schema/migration·지속 데이터, (c) 인증/권한·Secret/인증서, (d) 외부 서비스 계정·발신/PG 비용, (e) Oracle 설치·DB/네트워크·백업·배포, (f) 법률/약관·공개 출시·실결제. 각 패킷에는 현상·선택지/권장안·비용/고객 영향·정확한 변경 대상·rollback·독립적으로 계속할 수 있는 작업을 제시한다. 계획 승인만으로 이 개별 승인들을 대신하지 않는다.
5. S8의 판정은 **개발 완료 후보**다. 인수 준비 U0은 S5 전부터 조사 가능하지만 실제 공급자/Oracle 작업은 별도 승인 뒤. S8 뒤 [U1~U4](DEPLOYMENT_UAT_PLAN.md)에 따라 정확한 PR 후보를 staging에 배포하고 신산님 인수 승인을 받는다. UAT 불합격은 branch 수정→로컬/WSL→새 후보 배포→영향 회귀 순으로 반복하며 독립 범위는 진행한다.
