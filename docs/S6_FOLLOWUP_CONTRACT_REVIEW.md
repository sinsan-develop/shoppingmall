# S6 정산 후속 계약 대조 — B2 검토 자료

> 이 문서는 `WORK_PLAN_20260-10-09.md` B2의 구현 전 대조 자료다. `DESIGN.md`나 기존 `WORK_PLAN.md`를 변경하거나 DB 적용을 승인하는 문서가 아니다. 신산님의 권고안 승인 내용과 실제 코드 사이의 차이만 정리한다.

## 1. 정정 사건(A1)

| 항목 | 현재 동작 | 승인된 후속 계약과 구현 영향 |
|---|---|---|
| 원사건 | `settlement_events`에 정정 종류만 예약되어 있고 원사건 FK가 없다 | `originalEventId`가 기존 불변 사건을 가리킨다. 판매자·발생 당시 분류·조정 대상 항목은 서버가 원사건에서 얻는다. 타 판매자나 정정 사건 재참조는 거부한다. |
| 금액 | `amount_won > 0`; 집계는 종류별 양수 합계 | 요청은 양의 원화 정수 `amountWon`과 `increase`/`decrease` 방향을 분리한다. 대상 항목의 순합계에 방향을 반영하고 원사건·기존 완료 금액은 보존한다. 감소 누적은 원사건의 남은 순액을 넘지 않는다. |
| 시간 | 기존 수수료는 실제 발생시각을 요청받을 수 있음 | 정정은 서버 기록 시점에 새 사건으로 생성한다. 과거 완료 기간으로 소급하지 않는다. 5월 완료 뒤 7월 정정은 7월 근거와 5월 원사건 링크로 보인다. |
| 멱등성 | 수수료는 요청 UUID로 중복 방지 | 같은 UUID·같은 본문은 기존 결과, 다른 본문은 409. 같은 원사건의 동시 감소는 트랜잭션 잠금으로 직렬화한다. |
| 접근 | 관리자 수수료 입력과 판매자 자기 조회 | 관리자 세션+Origin 검증의 `POST /admin/settlement/corrections`만 새로 추가한다. 판매자 입력·타 판매자 자료 접근은 금지한다. |

예상 요청: `{ "originalEventId": "uuid", "requestId": "uuid", "direction": "decrease", "amountWon": 1500, "reason": "수수료 오입력 확인" }`. 응답은 정정 사건 ID·원사건 ID·대상 항목·방향·금액·서버 발생/기록 시각·사유를 포함한다. 입력 검증/권한·동시성·중복 응답은 C1/C1.2의 RED 시험으로 고정한다.

현재 `0020_s6_settlement.sql`은 `correction`의 상품/옵션 직접 열을 허용하지 않으므로 상품 근거는 원사건 연결을 따라 조회한다. 새 0022 후보는 기존 0020/0021을 수정하지 않고 링크·방향 및 제약을 추가한다. 과거 `correction` 행이 발견되면 원사건을 추정해 채우지 않고 이관 결정을 요구한다. 실패 시 앱은 이전 검증 commit으로 되돌리되 불변 장부 행을 삭제하거나 적용 migration을 역실행하지 않는다.

## 2. 분류 변경 후 완료 조회(A2)

현재 발생 사건은 `event.seller_category_id`로, 완료 기간은 `seller.category_id`로 필터링된다. 따라서 판매자가 X→Y로 이동하면 X의 과거 사건과 그 기간의 완료 표시가 갈라질 수 있다.

- 분류별 조회에서 완료 기간은 연결된 사건의 당시 분류별로 분해해 표시한다. X와 Y 사건이 함께 포함된 한 완료 기간은 X 조회에 X 사건의 고정 항목별 금액, Y 조회에 Y 사건의 고정 금액만 표시하고 전체 조회에는 기간 전체를 표시한다. 기간 ID는 동일하게 유지해 중복 완료로 오해하지 않도록 조회 범위를 명시한다.
- 사건 0건 완료는 완료 시점 판매자 분류 스냅샷으로만 귀속한다. 0023 후보는 이 스냅샷을 신규 완료부터 저장한다. 기존 0건 완료의 당시 분류를 증명할 수 없다면 현재 분류를 조용히 역사값으로 채우지 않고 migration/이관을 보류한다.
- 인쇄/PDF는 조회 응답의 동일한 분류 부분합·전체 합계를 사용한다. 판매자는 분류와 관계없이 자기 판매자 자료만 읽는다.

## 3. 검증·적용 경계(A3)

후보 SHA의 격리 PostgreSQL·실 API·Chromium·PDF 거래 E2E와 공유 `local-postgres/shoppingmall`의 migration/준비상태/권한 차단 읽기 smoke를 별개로 기록한다. 공유 DB에 불변 QA 거래 행을 만들지 않으므로 공유 DB 행 기반 E2E는 계속 `UNVERIFIED`다. 0022/0023의 공유 DB 실제 적용은 별도 대상 확인·승인·복구 절차 후에만 한다. 실제 발송·PG 실거래·Oracle·인수는 이 후속 계획의 검증 범위가 아니다.
