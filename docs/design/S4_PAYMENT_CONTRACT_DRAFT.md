# S4.1 결제 확인·모의 공급자 계약 — 검토 초안

상태: **신산님 검토·승인 전**. 승인된 `DESIGN.md` R05~R07과 `WORK_PLAN.md` S4를 구체화한다. 이 문서는 새 API·DB migration의 구현이나 공유 DB 적용, 실 PG 사용, Oracle 배포를 승인한 기록이 아니다.

## 1. 목적과 선택

S3의 결제대기 통합 주문 1건과 발송 주문 여러 건을 한 번의 검증된 결제로 확정한다. 고객이 결제 화면에서 돌아오거나 버튼을 눌렀다는 사실만으로 `PAID`가 되지 않는다. 서버가 공급자의 주문 식별자·승인 상태·금액을 확인하고, 중복·역순·만료 사건을 기록한 뒤 한 번만 재고와 쿠폰을 확정한다. 개발 중에는 실제 카드·PG 계정 없이 모의 공급자만 사용한다.

| 방안 | 장점 | 위험·판정 |
| --- | --- | --- |
| **권장: 결제 시도·검증 사건을 DB에 기록하고 모의 공급자를 같은 경계에 연결** | 지연·중복·재시도 근거가 남고 나중에 실제 PG로 교체 가능 | 0013 migration과 고객 API 계약의 별도 승인이 필요 |
| 주문 상태만 `PAID`로 바꾸는 단순 모의 버튼 | 초기 구현이 짧음 | 공급자 금액 대조·중복 사건·환불 원거래가 없어 S4 인수 기준 불충족 |
| 특정 PG SDK를 지금 주문 서비스에 직접 연결 | 해당 PG의 시험 화면을 빨리 볼 수 있음 | 시험상점 미준비이며 공급자 확정 전 결합·비용 위험이 있어 현재 제외 |

## 2. 범위와 비범위

- 이 초안은 **S4.1**만 다룬다. S4.2의 발송 주문별 전체·일부 취소와 환불 원장은 별도 계약으로 구체화한다. S4 PR은 S4.1·S4.2 검증을 묶어 한 Stage로 마친다.
- 결제 운영 모드는 기본 `disabled`다. `mock`은 `APP_ENV=development`와 `PAYMENT_MODE=mock`이 모두 명시된 로컬·승인된 WSL 개발 환경에서만 켜고, 외부 공개가 아닌 루프백 접근으로 제한한다. 이 조건이 다르면 시작 시 닫힌 상태로 실패하게 한다. 고객 화면에는 항상 **모의 결제**로 표시하며 Oracle 인수 환경과 운영 환경에서 mock을 실결제처럼 사용하지 않는다.
- 실제 PG 사업자·시험상점·키·서명 검증·공급자별 webhook URL, 카드 승인·부분환불은 U0 준비 및 별도 승인 후 연결한다. 공급자별 HTTP webhook의 실연동 성공은 이번 mock 결과로 주장하지 않는다.
- 카드번호·인증정보·공급자 원문 응답·민감 개인정보는 결제 사건 테이블에 저장하지 않는다. 기존 주문의 금액·상품·주소 스냅샷을 소급 수정하지 않는다.

## 3. 고객 API와 내부 공급자 경계 — 구현 승인 요청 대상

| 경로·경계 | 동작 |
| --- | --- |
| `POST /customer/checkout/orders/:id/payment-attempts` | 로그인한 해당 주문 구매자, 동일 Origin, UUID `Idempotency-Key`가 필요하다. 유효한 `PENDING_PAYMENT` 주문에만 시도 1건을 만든다. 같은 키·같은 입력은 같은 시도를 반환하고 다른 입력은 `409`; 타인 주문은 존재를 노출하지 않는다. 금액은 고객 입력이 아니라 주문의 `payable_won`을 쓴다. `mock` 모드에서만 `testOutcome: approve \| decline \| delay`를 허용하고 다른 모드에서는 거부한다. 응답은 시도 ID·모의 여부·현재 결과만 포함하며 카드정보는 없다. |
| `GET /customer/checkout/orders/:id/payment-attempts/:attemptId` | 해당 주문 구매자에게 그 시도의 `PENDING`·`APPROVED`·`DECLINED`·`REVIEW_REQUIRED`와 정수 원 금액만 보여준다. 조회는 상태를 변경하지 않는다. |
| 기존 `GET /customer/checkout/orders/:id` | 기존 주문 스냅샷을 유지하고 `PAID` 상태와 결제 시각이 생기면 그 사실을 표시한다. 서로 다른 발송 주문은 한 결제의 같은 확정 결과를 공유한다. 실패한 시도만으로 주문을 `PAID`나 `EXPIRED`로 바꾸지 않는다. |
| 내부 `PaymentAdapter`와 검증 사건 처리기 | `start`는 공급자 주문 ID를 생성/획득한다. `verify`는 서버가 공급자 식별자·주문 ID·승인액·결과를 확인해 정규화한 사건을 반환한다. mock은 동일 계약으로 승인·거절·지연·중복·역순을 주입하며, 정규화 사건 처리기는 공급자 교체 후에도 유지한다. 실제 공급자 HTTP callback 진입점·서명 방식은 공급자 확정 후 별도 계약이다. |

모의 성공 버튼 또는 브라우저 복귀는 단지 시도·확인 요청을 시작한다. `PAID` 기록은 내부 `verify`가 반환한 승인 근거와 주문 스냅샷의 원 단위 금액이 일치한 뒤에만 가능하다. 모의 지연은 조회에 `PENDING`으로 남고, 모의 거절은 같은 주문의 새 시도를 허용하되 만료 전까지만 가능하다.

## 4. 0013 영속 데이터 계약 — 구현 승인 요청 대상

기존 0000~0012 SQL과 기존 주문 행을 변경하거나 삭제하지 않는 전진 migration을 만든다. `0013_s4_payments.sql`은 다음만 추가·확장한다.

| 대상 | 필수 내용·제약 |
| --- | --- |
| `payment_attempts` 신규 | UUID, 통합 주문 ID, 공급자 코드(`mock` 또는 0원 주문의 `no_charge`부터), 공급자 주문 ID, 정수 승인 요청액, 고객 멱등 키·요청 지문, `PENDING`/`APPROVED`/`DECLINED`/`REVIEW_REQUIRED`, 생성·종료 시각. 주문+멱등 키와 공급자+공급자 주문 ID를 각각 유일하게 제한한다. |
| `payment_events` 신규 | UUID, 결제 시도 ID, 공급자 코드·사건 ID, 정규화 승인/거절 결과, 검증된 주문·공급자 결제 ID·정수 원 금액, 사건 지문·수신 시각·처리 상태(`PENDING_PROCESSING`/`APPLIED`/`REVIEW_REQUIRED`). 공급자+사건 ID 유일. 같은 사건 ID에 다른 내용은 성공으로 처리하지 않고 충돌로 기록한다. 카드정보·원문 payload는 저장하지 않는다. |
| `checkout_orders`·`shipment_orders` | 상태 제약에 `PAID`를 추가하고 통합 주문의 `paid_at`을 둔다. 기존 `ended_at` 제약도 `PAID`의 종료 시각을 허용하도록 확장한다. 금액 스냅샷·만료 시각은 불변. 기존 `PENDING_PAYMENT`/`EXPIRED` 행은 그대로 유효해야 한다. |
| `order_status_events` | `PAID` 사건을 허용하되 기존 접수·만료 이력을 덮어쓰지 않는다. 승인 근거는 `payment_events`와 연결해 추적한다. |

검증된 공급자 사건은 먼저 고유 키와 지문으로 `PENDING_PROCESSING`에 영속 기록한다. 별도 처리 거래에서 계정→주문→쿠폰 점유→예약→상품/옵션/재고의 고정 순서로 잠그고 상태를 확인한다. 정상 승인 1건일 때만 통합·발송 주문을 `PAID`, 예약을 기존 `CONSUMED`, 쿠폰 점유를 기존 `USED`로 전이하고, 옵션별 `on_hand_quantity`를 구매 수량만큼 한 번 차감한다. `sellable_quantity`도 같은 수량만큼 줄이되 이미 판매중지로 0이면 0을 유지한다. 재고·쿠폰 확정 중 하나라도 실패하면 **상태 변경 거래만** 취소하고 앞서 기록한 사건은 `PENDING_PROCESSING`으로 보존해 재처리한다. 성공 뒤 사건은 `APPLIED`로 표시한다. 중복 사건은 재고·쿠폰·상태를 다시 바꾸지 않는다.

저장된 결제예정액이 0원이면 PG를 호출하지 않는다. 서버가 같은 주문·재고·쿠폰 조건을 확인하고 `no_charge` 시도/사건을 0원으로 남겨 위의 단일 확정 거래를 수행한다. 0원도 브라우저 복귀만으로 `PAID`가 되지 않으며, 0원이 아닌 금액을 `no_charge`로 확정할 수 없다.

## 5. 만료·역순·실패의 안전 기준

- 만료 작업과 승인 사건이 겨루면 위 고정 잠금 순서로 하나만 정상 전이한다. 승인 전에 주문이 이미 `EXPIRED`가 되었다면 뒤늦은 승인 사실은 `REVIEW_REQUIRED`로 기록하고 **자동 출고·재고 소비·쿠폰 사용을 하지 않는다**. 금전 보정은 S4.2의 관리자 처리 대상으로 남긴다.
- 거절/통신 실패는 결제 시도에 남기고 주문은 만료 전 `PENDING_PAYMENT`로 유지한다. 동일 키 재시도는 기존 시도를 재조회하고, 새 시도는 새 키가 필요하다. 확인 불가를 성공으로 가정하지 않는다.
- 검증된 공급자 주문 ID가 다른 주문에 매핑되거나 승인액이 저장된 `payable_won`과 1원이라도 다르면 `PAID`를 금지하고 운영 검토 대상으로 기록한다. 브라우저가 보낸 금액·상태는 정본이 아니다.
- 기존 S3 만료 동작은 결제 성공 주문을 해제하지 않는다. 만료 직전·직후 callback, 중복 callback, 다른 사건 ID의 동일 승인, 순서가 뒤바뀐 승인/거절을 별도로 시험한다.

## 6. 검증·적용·복구

1. 기존 주문·예약·쿠폰·재고의 상태/잠금 순서를 먼저 회귀 시험으로 고정한다. RED에서 고객 복귀만으로 미확정, 1원 불일치, 중복·역순 승인, 만료 경합, 마지막 재고 경쟁, 타 구매자 접근, 동일 키 다른 본문을 재현한다.
2. 격리 PostgreSQL에 0000~0013 전체 적용·API/DB 계약과 mock 브라우저 성공/실패/재시도·390px/키보드 흐름을 GREEN으로 만든다. 로컬 test/typecheck/lint/build와 SSH 별칭 push→WSL 지정 checkout의 동일 SHA 시험을 분리 기록한다.
3. **공유** `WSL-server/local-postgres/shoppingmall`의 0013 적용은 SQL 해시·기존 행 영향·백업·복구 절차를 보여 별도 승인받는다. 승인 전에는 공유 DB에 적용하지 않는다. 시험 후 가상 주문·사건과 정확한 임시 컨테이너/포트/볼륨 잔류를 확인한다.
4. 오류 시 mock 결제 시작을 끄고 기존 주문/결제·감사 사건을 보존한다. 이미 승인된 금전 사건을 삭제하거나 0013을 임의 역적용하지 않는다. 원인별 보정 migration 또는 공급자 환급은 별도 결정한다.

## 7. 이 초안에서 요청하는 결정

신산님께서는 위 **S4.1 고객 API 2개와 기존 주문 조회 상태 확장, 내부 mock/검증 계약, 0013의 신규 2관계·기존 상태 제약 확장의 구현**을 승인할지 검토한다. 이는 0013의 공유 DB 적용, 실제 PG/Secret·비용, Oracle 배포, S4.2 환불 API·schema의 승인과 서로 다르다. 승인 전에는 이 문서와 읽기 전용 조사 외의 S4.1 구현을 시작하지 않는다.
