# S3.3 발송 주문·통합 결제 대상 계약 — 구현 승인

상태: 신산님이 아래 공개 API 2개와 `0012` 영속 관계 5개의 **구현**을 승인했고, 이후 `WSL-server/local-postgres/shoppingmall`에 `0012`를 적용하도록 별도 승인해 적용했다. 상위 정본은 `DESIGN.md` R02·R03·R05, `S3_PROMOTION_CONTRACT_DRAFT.md` 4~6절과 `WORK_PLAN.md` S3이다.

## 목표와 경계

- 고객의 유효한 15분 예약을 제출하면 한 통합 결제 대상(`checkout_orders`)과 발송 묶음별 주문(`shipment_orders`)을 **하나의 DB transaction**에서 저장한다. 농가 A 직접·농가 B 직접·어울몰 모아 발송이면 발송 주문은 정확히 3건이다. 어울몰 판매자도 다른 판매자와 같은 권한·상품 구조를 따른다.
- 이번 단계는 `PENDING_PAYMENT` 주문까지만 만든다. PG 승인·실결제·`PAID` 표시·환불/정산·실출고는 S4 이후이며 여기서 흉내 내지 않는다. 상품·배송 정책·혜택의 현시점 값으로 서버가 다시 계산하고 제출 당시의 금액·혜택 버전·상품/배송지 사실을 불변 스냅샷으로 저장한다.
- ACTIVE 예약은 주문 결제대기 동안 재고를 계속 선점한다. 결제대기 만료는 예약 만료보다 늦지 않고, 만료 처리 transaction에서 주문 `EXPIRED`, 예약 종료, 쿠폰 점유 해제를 함께 수행한다. 실제 결제 콜백이 생기는 S4는 결제 시도와 만료 경합을 별도 설계한다. S3.3에서는 재고 수량을 최종 판매로 차감하지 않는다.

## 승인된 공개 API — 구현 대상

| 경로 | 입력/반환 및 권한 |
| --- | --- |
| `POST /customer/checkout/orders` | 고객 세션·동일 Origin·UUID `Idempotency-Key` 필수. 본인 `reservationId`, 본인 활성 `addressId`, 기존 `PromotionSelection`, 화면에 표시된 정수 `expectedPayableWon` 제출. 성공 `201`에 통합 주문 ID·3발송 ID/금액·`PENDING_PAYMENT`·만료 시각, 같은 키/같은 내용 재시도 `200`에 동일 ID/스냅샷. 금액/예약/상품/정책/쿠폰/배송지 변경은 생성 없이 `409`; 위조 권한·타인 ID는 거부한다. |
| `GET /customer/checkout/orders/:id` | 본인 주문의 스냅샷·상태·발송별 금액/품목만 조회. 타인에게 주문 존재를 노출하지 않는다. 결제 완료로 오인할 표현은 쓰지 않는다. |

서버는 `account_id + idempotency_key`와 `reservation_id`를 각각 유일하게 제한한다. 같은 키에 다른 배송지/혜택/기대금액을 넣으면 `409`; 다른 키로 같은 예약을 재제출해도 새 주문을 만들지 않는다. 중복 요청은 계정→예약→옵션 재고→캠페인 ID 순으로 잠금을 얻고, DB 제약을 최종 안전망으로 사용한다. 응답 손실 뒤 재시도는 최초 주문 ID를 반환한다.

## 승인된 0012 migration — 구현·공유 개발 DB 적용 완료

기존 0000~0011 SQL/이력을 수정하지 않고 다음 다섯 관계만 additive로 추가한다. 기존 계정·상품·예약·프로모션 행의 삭제·초기화는 없다.

| 관계 | 정본 필드·제약 |
| --- | --- |
| `checkout_orders` | ID, 고객/예약 ID, 멱등 키·요청 지문, 본인 배송지 ID와 수령인/연락처/우편번호/주소 **스냅샷**, 할인 전 상품액·상품할인·배송비·배송지원·결제예정액(모두 정수 원), `PENDING_PAYMENT`/`EXPIRED`, 생성/만료/종료시각. 고객+키 및 예약 ID 유일. 금액 비음수·`결제예정액=상품액-할인+배송비-지원` CHECK. |
| `shipment_orders` | ID, 통합 주문 ID, 발송 key/방식/직접 판매자 ID(모아 발송은 null), 각 금액/상태. 통합 주문+발송 key 유일, 방식과 판매자 ID 조합 CHECK. 발송 합계가 통합 주문 합계와 일치하는지는 같은 transaction의 서비스와 실DB 시험으로 강제한다. |
| `shipment_order_lines` | 발송 ID, 상품/옵션/판매자 ID, 제출 시 상품명·옵션명·단가·수량·할인 배분·실상품 결제액 스냅샷. 발송+옵션 유일, 수량 양수·금액 비음수. 모아 발송 안에서도 원판매자 추적. 부분 취소의 실제 상품 환급액은 이 불변 값에서 출발한다. |
| `order_promotion_allocations` | 통합 주문·발송 주문, 쿠폰 사용 ID·캠페인/버전 ID, `goods_discount`/`shipping_support`, 해당 발송 배분 원액. 동일 사용+발송+종류 중복 금지. 화면 견적을 새로 계산한 결과가 아니라 제출 시점의 최종 배분을 보존한다. |
| `order_status_events` | 주문 ID, `PENDING_PAYMENT` 또는 `EXPIRED` 전이, 행위자/시각/사유. 최초 접수·자동 만료를 감사 가능하게 기록. S4가 결제·취소 사건을 확장할 때 이력을 덮어쓰지 않는다. |

상품할인액은 먼저 대상 상품의 할인 전 금액 비율로 발송 주문에 원 단위 배분한다. 다시 같은 발송 안의 대상 품목 금액 비율로 배분해 품목 합계=발송 할인액, 발송 합계=통합 할인액을 만족시킨다. 나머지 1원 우선순위는 발송 key·옵션 ID의 안정적인 순서로 고정한다. 무료배송 5만 원 판정은 각 발송의 **할인 전** 상품금액이며, 배송비 지원은 실제 부과 배송비 이하이다. 할인 후 무료배송을 재판정하거나 남은 발송에 할인액을 재배분하지 않는다.

## 검증·안전·복구

- TDD: 서로 다른 직접 판매자 2+모아 발송 1의 단일 통합 주문·3발송, 49,999/50,000원 경계, 52,000원 발송의 할인 후 무료배송 유지, 1원 잔액 배분, 다른 계정/만료 예약·품절·배송 불가·잘못된 Origin/배송지·초과 쿠폰 한도·동시 제출·멱등 재시도·요청 지문 충돌을 격리 DB에서 검증한다. 저장 실패면 주문·쿠폰 점유·예약 상태 모두 원상복귀한다. 만료 처리에서는 주문/예약/쿠폰만 종료하고 타 주문·이미 결제된 주문은 보존한다.
- 로컬 test/typecheck/lint/build, 정확한 커밋을 SSH 별칭으로 push→WSL 지정 checkout fast-forward, 격리 0012 전체 migration 재현·실DB 전체 suite·실제 브라우저 제출/재시도/권한/모바일·키보드, QA 자료 0을 거친다. 공유 `local-postgres/shoppingmall` 0012 적용은 SQL·영향·백업·복구 절차를 보여 별도 승인을 받는다. Oracle staging·사용자 인수·실 PG는 아직 하지 않는다.
- 장애 시 주문 제출을 중지하고 마지막 검증된 `main` 코드로 되돌리되 이미 저장한 주문·감사·혜택 점유를 무단 삭제하지 않는다. additive 0012를 임의로 되돌리거나 DB 전체를 초기화하지 않는다. 원인/상태를 조회한 뒤 보정 migration은 별도 승인한다.
