# S3.2 프로모션·쿠폰 상세 계약 초안

> 상태: 신산님 검토 대기. 2026-10-03의 “계속하자”는 목록 선택·코드 입력을 하나의 쿠폰 사용 체계로 설계하는 방향에 대한 진행 지시로 해석했다. 이 문서는 공개 API, DB schema·migration, 운영 혜택 발행 또는 공유 DB 적용의 실행 승인이 아니다.

## 1. 목적과 범위

어울몰 고객이 사용 가능한 쿠폰을 목록에서 고르거나 코드를 직접 입력해 한 번의 통합 결제에 적용할 수 있게 한다. 관리자는 할인 쿠폰과 발송 주문별 배송비 지원을 발행·중지하고 사용 이력을 확인한다. 서버는 판매 가능 상태·승인된 배송 정책·현재 상품금액을 재검사해 견적을 계산한다. 결제·환불·정산은 이때 확정한 금액과 발생 근거를 참조한다.

기존 [범위 보완안](DELIVERY_SCOPE_ADDENDUM.md)의 통합 결제당 할인 쿠폰 최대 1개, 발송 주문별 배송비 지원 최대 1개, 할인 전 상품 소계로 무료배송 판정, 무료배송에 지원금 중복 적용 금지를 유지한다. 개인별 추천·포인트·등급·광고 과금·운영 비용 부담 자동 결정은 포함하지 않는다. 홈 기획전/배너는 노출 콘텐츠이며 금액 혜택의 정본이 아니다.

## 2. 선택한 구조와 대안

- **권장 초안 — 단일 혜택 원장:** 관리자 혜택 규칙의 버전, 고객 발행/코드 획득, 예약·사용·해제 사건을 연결한다. 목록 선택과 코드 입력은 같은 혜택 ID를 찾는 두 경로일 뿐 금액 계산·한도 검사는 같다. 주문 당시 버전과 금액 배분은 변경 불가능한 스냅샷으로 보존한다.
- **대안 — 경로별 별도 엔진:** 목록 쿠폰과 코드 쿠폰에 별도 사용 횟수와 계산을 둔다. 초기 구현은 국소적일 수 있으나 두 경로로 같은 혜택을 중복 사용하거나 취소 시 다른 규칙을 적용할 위험이 있어 채택하지 않는다.

관리자 변경·중지는 새 주문에만 적용한다. 이미 확정한 주문의 할인·배송비·사용 이력은 덮어쓰지 않는다. 한 관리자 혜택 버전에 코드와 직접 발행을 동시에 연결할 수 있지만, 고객의 최종 적용은 중복 없이 한 번만 가능하다.

## 3. 관리자 설정·고객 획득

| 항목 | 제안 계약 |
|---|---|
| 유형 | 상품/주문 상품금액 할인(정액 또는 정률), 발송 주문 배송비 지원(정액 한도), 별도 홈 배너 |
| 대상 | 승인·판매 가능 상품 옵션 ID와 판매자 ID의 명시적 집합. 비어 있으면 전체 대상. 판매자 분류나 원산지로 암묵 제한하지 않음 |
| 기간 | 관리자 화면은 한국시간으로 입력·표시, DB는 시각으로 저장. 시작 포함·종료 미포함. 견적과 주문 접수 시 서버 시각으로 재검사. 접수된 주문의 정상 결제 결과가 늦게 도착해도 해당 주문 스냅샷을 유지 |
| 최소 구매액 | 해당 할인에 적격한 상품의 할인 전 금액 합계가 설정액 이상. 배송비·다른 할인은 포함하지 않음 |
| 정액·정률 | 원화 안전 정수. 정액은 적격 상품금액 이하로 제한하고 정률 계산의 1원 미만은 버린 뒤 관리자 지정 상한과 적격 상품금액 중 작은 값으로 제한. 0원·음수·상한 없는 무제한 정률은 등록 거부 |
| 한도 | 직접 발행은 총 발행 수 제한, 모든 경로에는 총 사용 수와 계정별 사용 수 제한. 사용 중 예약도 사용 한도에 포함하고 실패·만료 시 해제 |
| 코드 | 첫 범위는 관리자가 만든 공용 코드: 고객이 입력하면 서버가 동일 혜택을 찾아 계정별 사용 한도를 적용. 직접 발행받은 쿠폰은 고객 목록에 표시. 개인별 고유 코드 생성은 이번 범위에 포함하지 않음 |
| 중지 | 관리자만 중지 가능. 중지 후 신규 견적·쿠폰 점유·주문 접수 불가; 이미 접수된 주문의 정상 결제 결과와 금액은 불변. 수정은 새 규칙 버전으로 기록 |

코드는 대소문자·주변 공백을 정규화한 뒤 정확히 비교하고, 고객에게 다른 계정의 발행 내역과 내부 한도 수치는 노출하지 않는다. 코드 시도는 인증된 고객에게만 허용하고 남용 방지 한도를 둔다. 판매자는 혜택을 발행·중지할 수 없으며 자기 주문에 반영된 금액만 조회한다. 관리자 변경·수동 재발행은 actor·시각·사유와 함께 감사 기록을 남긴다.

## 4. 견적·사용 상태 전이

1. 고객이 장바구니에서 재고 예약을 만들고, 서버가 상품 옵션·판매자·현재 가격·공개 상태·승인 배송 정책을 재확인한다. 목록의 쿠폰 ID 또는 입력 코드 중 하나를 선택한다. 둘을 함께 지정하거나 동일 혜택을 중복 지정하면 거부한다.
2. 서버는 할인 전 발송 묶음별 상품 소계로 각 배송비와 5만 원 무료배송 여부를 먼저 결정한다. 쿠폰 적격 상품금액으로 최소 구매액·정액/정률 상한을 계산한다. 적격 금액만 기존 결정적 원 단위 배분 함수에 넣는다.
3. 배송비 지원은 각 발송 묶음의 실제 배송비 이하로 적용한다. 무료배송이면 지원액은 0원이고 현금성 상품할인으로 전환하지 않으며 0원 혜택을 사용 완료로 처리하지 않는다. 고객 견적에 원가·할인·지원·실제 결제 상품/배송금액과 판매자별 묶음을 구분해 보여준다.
4. 화면의 견적은 권리 확보가 아니다. 주문 제출(S3.3)은 같은 DB transaction 안에서 현재 혜택 버전·기간·대상·한도·재고·금액을 다시 검사하고 쿠폰 사용 자리를 원자적으로 점유한다. 동시 요청은 DB 잠금/제약으로 한도 내 한 건만 성공한다. 같은 고객·멱등 키 재시도는 같은 결과를 반환한다.
5. 점유는 결제 확정 전 상태다. 결제 실패, 주문 제출 실패 또는 결제 시도 없이 예약 만료로 확정되지 않으면 점유를 해제한다. 접수된 결제 시도는 정해진 만료/실패 처리 전까지 점유를 유지한다. 결제 완료 사건은 접수 당시 스냅샷을 기준으로 한 번만 사용 완료로 바꾼다. 늦거나 중복된 결제 콜백은 주문·쿠폰 상태를 멱등 재검증하며 임의 재사용시키지 않는다. 결제 시도 만료와 늦은 승인 충돌은 S4 결제 상태 계약에서 환불/보류 분기까지 정한다.
6. 결제 완료 후 전체 취소·일부 발송 주문 취소에도 쿠폰을 자동 복원하지 않는다. 일부 취소는 취소 대상 묶음에 이미 배분된 할인액을 반영한 실제 결제 상품금액만 환불 계산에 사용하고, 남은 묶음의 할인액은 다시 계산하지 않는다. 예외 재지급은 관리자 새 발행과 감사 이력으로 처리한다. 배송비 환급·반송비의 별도 적법성 정책은 S4 계약을 따른다.

## 5. 데이터·API 변경 제안 — 아직 실행 미승인

새 `promotions` 경계에 혜택/불변 규칙 버전, 공용 코드, 직접 발행된 고객 쿠폰, 사용 자리 점유·해제·확정 이력을 분리한다. 원본 발행·이력은 삭제 대신 중지/종결 상태로 보존한다. 캠페인 총한도에는 완료 건과 유효한 점유 건을 함께 포함하고, 계정·혜택별 한도는 두 획득 경로가 공유한다. DB는 고객/혜택/주문·예약 참조, 유효 상태, 중복 사용 방지와 동시 경쟁 제약을 가져야 한다. 실제 테이블·인덱스·migration SQL은 S3.2 구현계획 검토 시 정확한 변경 목록으로 제시한다.

제안 공개 API는 관리자 혜택 버전 등록·조회·중지/직접 발행, 고객 사용 가능 쿠폰 목록·코드 확인·적용 견적이다. 인증/권한·Origin 검사를 기존 경계와 동일하게 적용한다. 주문 제출과 PG 콜백의 원자적 사용 확정은 S3.3/S4 API 계약과 연결하며 별도 명세 승인 전 경로·필드명을 확정하지 않는다. API 오류는 `만료`, `대상 아님`, `한도 소진`, `이미 사용`, `판매 불가`를 구분하되 다른 계정의 쿠폰 존재를 누설하지 않는다.

S3.3 발송 주문마다 옵션/판매자·원금·할인 배분·배송비·배송지원·실제 결제액과 혜택 규칙 버전을 저장한다. 통합 결제 ID와 발송 주문 ID를 별도로 보존한다. S4 환불·S6 정산 발생 자료는 이 스냅샷을 참조하며 현재 캠페인 설정을 재계산하지 않는다.

## 6. 검증 사례와 안전 경계

- 동일 쿠폰을 목록과 코드로 번갈아 지정해도 한도와 사용 기록이 하나인지, 타 계정 직접 발행 쿠폰을 ID로 열람·적용할 수 없는지 확인한다.
- 판매자/옵션 대상 제외, 시작 직전·종료 시각, 최소 구매액 경계, 고정 할인 상한·정률 반올림, 49,999원/50,000원 무료배송 경계, 52,000원에서 5,000원 할인 후 무료배송 유지를 시험한다.
- 서로 다른 판매자 직접 발송과 어울몰 발송을 한 장바구니에 넣어 발송 묶음별 배송지원 최대 1개, 무료배송 묶음 지원 0원, 통합 할인 원 단위 합계 일치를 시험한다.
- 마지막 1회 쿠폰에 두 계정/두 요청이 경쟁할 때 한 건만 점유·확정되는지, 실패·만료 해제 뒤 다시 사용할 수 있는지, 중복 주문/콜백·중지 직후 경합에서 사용 한도를 넘지 않는지 시험한다.
- 결제 후 전체·일부 취소에서 쿠폰 자동 복원 없음, 기존 발송 주문 할인액 불변, 환불·정산 발생 근거가 주문 스냅샷과 일치하는지 시험한다.
- 로컬 RED→GREEN·typecheck/lint/build 뒤 지정 WSL checkout의 exact SHA로 정식 개발 DB API/DB·실브라우저 흐름을 검증하고 고유 QA 계정·상품·쿠폰·주문·컨테이너를 정확히 정리한다. 실제 PG/Oracle/운영 혜택과 고객 인수는 이 검증에 포함하지 않는다.

## 7. 승인 경계·복구

이 초안의 검토/승인은 **상세 설계** 승인이다. 관리자·고객 공개 API 계약, 영속 schema/migration, 공유 `local-postgres/shoppingmall` 적용, 실제 운영 혜택 값·예산·회계 부담, Oracle 인수 배포는 각각 적용 대상과 영향을 명시해 필요한 별도 승인을 확인한다. 승인 전에는 기존 순수 금액 계산을 공개 견적에 연결하거나 혜택을 발행하지 않는다. 새 테이블은 격리 DB migration/복원 시험 후 공유 DB에 적용하며 기존 주문·계정 자료를 삭제하지 않는다. 실패 시 신규 발행·주문 제출을 중지하고 정확한 DB/커밋 상태와 복구 방법을 보고한다. 운영 DB 자동 복원·기존 migration 삭제는 하지 않는다.
