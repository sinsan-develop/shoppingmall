- 상태: 기존 제품 설계 범위는 승인됨. 이번에 추가한 계정 초기 설정·가입·복구 설계의 세부 정책은 아래 7절의 미확정 사항을 남긴 검토안이다. 화면 시안·외부 계약·개발환경 준비와 제품 구현은 이 문서 수정만으로 승인되지 않는다.

- 변경 이력: 2026-09-26 최초 초안 작성 후 신산님이 설계서 범위 승인. 2026-10-09 신산님 지시로 S6 정산 계약을 R09에 반영. 2026-10-10 `docs/design_change.md`에 기록된 A1·A2 설계 결정과 A3 검증 경계를 반영하고, G4의 정정 사건 발생 당시 분류 귀속을 명문화. 같은 날 신산님 요청에 따라 관리자 최초 비밀번호 설정·가입·비밀번호 찾기 요구를 R13·R14와 계정 흐름에 추가했다. 기존 론칭판 문서는 참고만 사용.

## 1. 목표와 범위

어울몰은 산지 정보와 출고 조건을 확인하고 농산물을 구매할 수 있는 전국 대상 단일 브랜드몰이다. 상품 산지는 특정 지역으로 제한하지 않는다. 첫 출시 범위는 고객 웹·iOS/Android 앱, 판매자·관리자 웹, 상품·재고, 분할 주문·통합 결제, 배송·클레임, 농가별 정산 자료다. 오픈마켓, 자동 송금·자동 최종 지급액 결정, 해외 판매와 개인화 추천은 첫 출시 범위가 아니다. 성공 지표와 잠정 목표값은 PRD 10절을 따르며 실제 운영 자료로 보정한다.

## 2. 역할과 권한

| 역할 | 허용 범위 | 금지·승인 경계 |
|---|---|---|
| 고객 | 상품·산지 조회, 장바구니·구매, 배송 조회, 문의·리뷰·클레임 | 판매·관리 설정 불가 |
| 판매자(농가·어울몰) | 자기 담당 상품·재고·발송 주문·운송장 처리, 변경 요청 | 다른 판매자 자료 변경 불가. 일반 고객 공개 변경은 관리자 승인 전 미반영. 환불 최종 결정·정산 완료 불가 |
| 관리자 | 전체 상품·정책·승인, 고객 환불 결정·처리, 농가별 기간 정산 완료 표시 | 요청과 승인을 별도 역할·행위로 기록. 동일인이 판매자이기도 해도 권한을 합치지 않음. 공개 가입·최초 접속만으로 관리자 권한을 부여하지 않음 |

품절·재고 0개에 따른 구매 차단은 즉시 반영한다. 재고 증가·품절 해제는 승인 후 반영한다. 실제 출고·운송장 입력은 고객에게 즉시 표시한다. 서버가 매 요청에서 역할과 판매자 소속 범위를 확인한다.

## 3. 핵심 계약과 수용 기준

| ID | 요구·수용 기준 |
|---|---|
| R01 | 고추·고춧가루·양파·마늘·블루베리를 가상 옵션·가격·재고로 시험한다. 초기 실제 값은 인수 준비 때 관리자가 설정한다. 산지 등록 제한은 없다. |
| R02 | 각 품목은 농가 직접 발송 또는 어울몰 발송 중 하나를 갖는다. 한 발송 주문에 두 방식이나 서로 다른 직접 발송 농가를 섞지 않는다. 장바구니는 함께 담을 수 있고 결제는 한 번에 한다. |
| R03 | 기본 배송비 3,000원과 무료배송 5만 원은 각 발송 주문의 할인 전 상품금액에 적용한다. 판매자 변경 요청은 관리자 승인 후 자기 담당 범위에 반영한다. |
| R04 | 재고 0개·품절은 구매를 즉시 막고 결제 직전 재검증한다. 늘어난 재고·품절 해제는 승인 전 판매 가능 상태가 되지 않는다. |
| R05 | 통합 할인은 대상 상품의 할인 전 금액 비율로 발송 주문에 배분하고 원 단위 합계를 맞춘다. 중복 제출·콜백·지연·역순 결제 이벤트로 중복 주문이나 초과 판매가 생기지 않는다. |
| R06 | 출고 전 적법한 발송 주문 전체 취소는 실제 결제한 상품금액과 배송비를 환불한다. 상품 일부만 취소해 무료배송 기준 아래가 되어도 새 배송비를 청구하지 않는다. 다른 발송 주문은 유지한다. |
| R07 | 출고 후 환불은 사유별로 구분하고 관리자만 최종 결정·실행한다. 배송비·반송비와 약관은 법률 검토 전 미확정이다. |
| R08 | 판매자는 담당 주문의 출고·택배사·운송장을 입력한다. 마감 이후 주문은 다음 출고 가능일을 안내한다. 관리자 정정은 사유·전후 상태·고객 안내를 기록한다. |
| R09 | 어울몰 자체 판매자를 포함한 전체·판매자 분류·개별 판매자의 항목별 발생일 기록과 임의 기간 합계, 판매자별 소계·원주문/상품 근거, 관리자 개별 완료를 제공한다. 완료 당시 포함 사건과 항목별 금액을 고정하고 늦게 기록된 사건은 별도 표시한다. 전체·분류 일괄 완료는 허용하지 않는다. 조회·완료 자료는 브라우저에서 인쇄하거나 PDF로 저장한다. 최종 지급액 결정·송금은 오프라인이다. |
| R10 | 상품 다중 사진·대표 사진·미리보기를 제공한다. 판매자 공개 제안은 승인 전 고객에게 보이지 않는다. 요청·승인·주문·클레임 이력을 행위자·역할·시각·사유와 함께 보존한다. |
| R11 | 고객 웹과 앱은 동일한 서버 가격·재고·주문 정책을 사용한다. 고객 문의·리뷰, 판매자/관리자 운영 예외 조회, 개인정보·권한·업로드 방어를 포함한다. |
| R12 | 고객 배송지·주문 내역·알림 설정·탈퇴 안내, 찜·재입고 알림, 구매 확정 고객 리뷰/이미지·문의, 기본 쿠폰·프로모션을 첫 출시 범위에 포함한다. 구체적인 실판매 혜택 값과 알림 채널 실연동은 인수 준비 때 확인한다. |
| R13 | 정식 초기 관리자(`admin` 역할) 계정이 존재해야 하며, 그 계정의 소유자가 최초 사용 전에 자신의 비밀번호를 설정한다. 공통·사전 공개된 초기 비밀번호, 첫 방문자의 관리자 권한 선점, 시험용 관리자 자격정보의 운영 전용을 허용하지 않는다. 관리자 식별자·소유 확인·초기 설정 수단은 공개 가입과 분리한다. |
| R14 | 로그인 화면에서 `가입하기`와 `비밀번호 찾기`로 이동할 수 있어야 한다. 가입 및 재설정은 서버의 본인 확인·역할 정책을 거쳐야 하며, 공개 화면에서 관리자 권한을 만들 수 없다. 개발 전용 mock 전화 가입을 정식 가입·복구 기능으로 간주하지 않는다. |

### R09 상세 — 승인된 정산 계약

- 매출·수수료·배송비·할인·배송비 지원·환불은 발생 시각, 판매자와 **발생 당시 판매자 분류**, 원결제·환불/원주문·발송 주문·상품/옵션 근거를 가진 불변 사건으로 기록한다. 동일 원사건의 중복 기록은 막는다. 상품 매출·할인·환불은 원 판매자, 배송비는 발송 담당 판매자 근거로 구분한다. 어울몰 자체 판매자도 다른 판매자와 같은 조회·완료 단위다.
- 수수료는 관리자가 실제 발생 시각·원화 금액·사유와 요청 식별자를 입력하는 사건이며 재시도로 중복 기록되지 않는다. 수수료율·비용 부담 주체·최종 지급액 가감 방향을 시스템이 추론하거나 자동 확정하지 않는다. 잘못된 장부 사건은 기존 행을 덮어쓰거나 삭제하지 않고 사유 있는 별도 정정 사건으로 추적한다.
- 정정은 관리자 전용 `POST /admin/settlement/corrections`로 원사건을 지정해 새 불변 `correction` 사건을 기록한다. 금액은 양의 원화 정수, 방향은 `increase` 또는 `decrease`로 별도 저장하고 대상 항목 종류·판매자는 원사건에서 서버가 결정한다. **정정 사건의 판매자 분류 ID·명칭은 원사건 분류를 복사하지 않고 정정 발생 당시 해당 판매자의 분류로 고정한다.** 예를 들어 분류 X에서 발생한 원사건을 판매자가 Y로 변경된 후 정정하면, 원사건은 X에 그대로 두고 새 정정 사건은 Y에 귀속한다. 관리자 사유·요청 UUID·서버 기록 시각과 원사건 링크를 보존한다. 정정의 정정은 허용하지 않고 감소 정정은 원사건의 남은 순액을 넘지 못한다. 같은 UUID·같은 내용의 재시도는 같은 사건을 반환하며 다른 내용의 재사용은 충돌로 거부한다. 동시 감소 요청도 원사건 기준으로 직렬화한다. 정정은 실제 기록일의 새 사건으로 표시하며 원행과 이미 완료한 기간의 고정 금액을 바꾸지 않는다. 관리자 화면·조회·인쇄에는 원사건·방향·금액·사유가 같은 근거로 표시되고 판매자는 자기 범위만 읽는다.
- 관리자는 **판매자 한 명씩** 기간 완료를 기록한다. 같은 판매자의 겹치는 완료 기간은 거부하고 서로 다른 판매자의 완료 상태는 독립이다. 사건이 없는 판매자의 0원 완료도 허용한다. 완료 시점에 포함된 사건 ID를 불변으로 연결해 그 기간의 항목별 금액과 원거래 구성을 고정하며, 뒤늦게 기록된 사건 때문에 과거 완료액을 다시 계산하거나 완료 상태를 재개하지 않는다.
- 이미 완료한 기간의 발생일로 늦게 입력된 사건은 원발생일·기록일·원주문·사유를 보존해 **완료 후 추가 발생**으로 별도 조회·인쇄한다. 완료 당시 합계에는 넣지 않는다. 5월 판매·완료 뒤 7월에 실제 환불이 발생하면 환불은 7월 사건으로 기록하고 5월 원주문·품목에 연결한다.
- 관리자 조회는 전체·판매자 분류·개별 판매자 모두 판매자별 구획과 소계·전체 합계를 제공하며, 판매자는 자기 자료만 읽을 수 있다. 전체 조회의 완료 이력에는 완료 기간 전체의 고정 항목별 금액을, 늦은 사건에는 별도 구획·합계를 표시한다. 화면과 브라우저 인쇄/PDF 저장은 같은 조회 근거를 사용한다. 판매자의 완료·타 판매자 조회와 전체·분류 일괄 완료는 허용하지 않는다.
- 판매자 분류별 과거 완료 조회는 **현재 분류가 아닌 완료에 연결된 사건의 발생 당시 분류**를 기준으로 한다. 한 완료 기간에 서로 다른 분류의 사건이 함께 있으면 분류 조회에는 해당 분류 사건의 고정 금액과 완료 근거만, 전체 조회에는 기간 전체의 고정 금액을 보인다. 사건이 없는 0원 완료는 완료 당시 판매자 분류 스냅샷에 귀속한다. 기존 완료 자료의 역사적 분류를 알 수 없다면 현재 분류로 조용히 소급 확정하지 않고 이관 여부를 별도로 결정한다.

### R13·R14 상세 — 계정 초기 설정·가입·복구 변경안

- **확정 요구:** 초기 관리자는 시험 계정과 별개의 정식 계정으로 준비하고 소유자가 최초 사용 시 비밀번호를 직접 설정한다. 로그인 화면에는 가입·비밀번호 찾기 진입점이 있어야 한다. 화면의 역할 선택값이나 최초 방문 사실만으로 계정 생성·관리자 권한 부여·비밀번호 변경을 허용하지 않는다.
- **권고 흐름:** 신뢰할 수 있는 운영 절차로 초기 관리자 식별자를 사전 지정하고, 해당 소유자에게 만료·1회용 설정 수단을 전달한다. 소유 확인과 설정 수단 검증이 끝나기 전에는 관리자 세션을 만들지 않는다. 구매자는 본인 확인을 거쳐 직접 가입하고, 판매자는 신청·관리자 승인 뒤 자기 판매자 소속과 역할을 받는다. 관리자는 공개 가입 대상에서 제외한다. 이미 존재하는 계정에는 중복 가입으로 새 역할을 주지 않는다.
- **비밀번호 찾기 권고 흐름:** 등록·검증된 연락 수단으로 만료·1회용 재설정 수단을 전달한다. 화면 응답으로 계정 존재 여부를 드러내지 않고, 재설정 수단은 재사용할 수 없게 처리한다. 비밀번호 변경 후 기존 세션을 무효화하고 당사자에게 변경 사실을 알리며, 요청·성공·실패·재발급을 감사 이력에 남긴다. 발급·검증·로그인에는 남용 방지 제한을 둔다.
- **현재 구현과의 경계:** 현 이메일/비밀번호 로그인과 개발용 mock 전화 가입·QA 관리자 계정은 위 초기 설정·정식 가입·복구의 구현 증거가 아니다. 비밀번호 해시·권한·세션의 기존 안전 계약을 유지하면서 별도 구현·시험·인수 계획을 세운다. 실제 발송 공급자 없이 시험할 때는 모의 발송과 실제 수신 미검증을 구분한다.
- **미확정 정책:** 초기 관리자 로그인 식별자(`admin`이라는 문자 그대로의 ID인지 이메일인지 포함), 소유 확인 및 일회용 수단 전달·재발급 절차, 구매자 확인 수단, 판매자 신청·승인 정보, 재설정 수단의 구체적 만료 시간·발송 공급자는 후속 작업계획과 인수 준비 전에 결정한다. 이 문단의 권고 흐름은 해당 미확정 사항을 자동 승인하지 않는다.

## 4. 데이터·외부 시스템 경계

- 개념 엔터티: 계정/역할/판매자 소속, 초기 관리자 소유 확인·1회용 설정/재설정 수단·세션 폐기 이력, 농가, 상품/옵션/이미지, 재고·예약, 정책·변경 요청·승인, 통합 결제와 발송 주문/품목, 결제·환불 이벤트, 출고·운송장, 문의·리뷰·클레임, 판매자·당시 분류별 불변 정산 발생 기록·원사건에 연결된 정정 사건·판매자별 완료 기간·완료에 포함된 사건 연결·0건 완료 시점의 판매자 분류 스냅샷, 감사 이력. 기존 0020·0021 정산 구조는 [정산 계약](../S6_SETTLEMENT_CONTRACT_PROPOSAL.md)과 [완료 금액 고정 설계](../S6_COMPLETED_AMOUNT_DESIGN_PROPOSAL.md)를 따른다. 정정·분류 이력용 추가 schema/migration의 공유 DB 실제 적용은 별도 환경 승인 경계다.
- 결제 금액의 정본은 서버 재계산 결과다. PG 응답을 주문·금액과 대조하며 결제수단의 민감 정보를 직접 저장하지 않는다. 통합 결제와 발송 주문은 별도 식별·연결한다.
- 고객 환불 기록과 농가 정산 항목은 연결하지만 자동 가감 부담·최종 지급액을 결정하지 않는다. 예를 들어 5월 판매를 5월에 정산하고 7월 환불하면 7월 발생 기록에 5월 원주문을 연결한다.
- 개발은 mock/sandbox와 시험 계정을 사용한다. PG 계약·요금, Oracle 환경, 외부 로그인·문자·메일·앱 빌드의 실제 검증 범위는 인수 준비 시 결정한다. 실연동이 없으면 결과를 실검증으로 표시하지 않는다.
- 개인정보 보관·파기와 출고 후 환불 약관은 법률·운영 검토 전 미확정이다. 시험 중 실제 고객 정보·실결제·실발송을 사용하지 않는다.

## 5. 화면과 흐름

- 고객: 홈/검색/목록 → 상품 상세 → 장바구니 → 발송 주문별 배송비와 통합 결제 확인 → 주문 완료 → 주문별 출고·배송 조회 → 문의·리뷰·클레임.
- 판매자: 담당 상품·사진/재고 → 변경 요청 → 승인 상태 확인; 담당 주문 → 포장·출고·운송장 입력. 농가·어울몰 판매자의 화면 절차는 같다.
- 관리자: 전체 상품·정책·판매자 요청 승인 → 주문·결제·환불·배송 예외 처리 → 전체/분류/개별 판매자의 발생일·기간 정산 자료와 완료 후 추가 발생 구분 → 판매자별 개별 완료 표시.
- 계정: 로그인 → 가입하기(역할별 허용 경로) 또는 비밀번호 찾기 → 본인 확인·설정/재설정 → 로그인. 초기 관리자는 공개 가입 대신 별도 소유 확인·비밀번호 설정 경로를 거친다. 만료·재사용·잘못된 수단에는 권한이나 세션을 주지 않는다.
- 필수 화면 상태: 로딩·빈 목록·오류·권한 없음·저장 대기·승인 대기·품절·결제 실패·부분 취소·출고 지연. 실제 경로명은 미확정이다.

## 6. 품질·운영과 완료 기준

- 접근권한/IDOR, 요청 위조·스크립트 삽입, 로그인·결제 남용, 이미지 업로드 형식·크기, 결제 멱등성·재고 경쟁, 금액 배분·부분 환불을 자동/실제 QA로 검증한다.
- 계정 변경은 초기 관리자 선점·공통 비밀번호·공개 관리자 가입 차단, 역할 승격 차단, 가입 중복, 재설정 계정 존재 추측 방지, 1회용 수단의 만료·재사용·경합, 변경 후 기존 세션 폐기와 감사 이력을 역할별 자동/실제 QA로 검증한다. 이메일·문자 등 외부 채널의 실제 수신 여부는 모의시험과 별도로 표시한다.
- 판매·환불·정산·승인의 상태와 감사 이력을 추적한다. 운영 예외 목록에서 미승인, 실패 결제, 미출고·지연, 미처리 문의를 확인한다.
- 고객/판매자/관리자 매뉴얼과 시험 자료 재생성, 백업 복원·복귀 절차를 작성한다. 로컬/WSL 개발 검증과 Oracle 인수 결과는 별도 증거다.
- 정산 후속 검증은 같은 후보 코드의 WSL 일회용 격리 PostgreSQL에서 실제 API·브라우저·PDF 거래 경로를 검증하고, 공유 개발 DB에서는 승인된 migration·준비상태·권한 차단의 읽기 검증을 별도로 수행한다. 공유 DB에 불변 가상 정산 거래 행을 만들지 않으며 그 DB의 거래 행 기반 E2E는 미검증으로 표시한다. 격리 DB의 통과를 공유 DB 거래 검증 통과로 바꾸지 않는다.
- 개발 완료는 승인된 [개발 작업계획](../WORK_PLAN.md)의 실제 검증 충족으로만 판정한다. 운영 출시·사용자 인수는 별도 설치·배포 계획과 승인·실연동 검증이 필요하다.

## 7. 미확정 및 승인 경계

화면 시안·로고의 최종 표현, 출고 후 환불·반송비 법률/약관, 실판매 옵션·가격·초기 수량, 실제 택배사, PG·발송·이미지 공급자와 요금, Oracle 서버, 앱 빌드·외부 로그인 실검증 범위, 개인정보 보관 기간은 미확정이다. 계정 변경의 초기 관리자 식별자·소유 확인/전달·재발급, 구매자 확인 수단, 판매자 가입 승인 절차, 일회용 수단 만료 시간·실 발송 연동 역시 미확정이다. 정정 사건과 판매자 분류 변경 후 완료 이력의 계약은 R09 상세에 확정했으나, 이 설계 반영만으로 해당 코드·공유 DB migration 적용·실제 검증이 이루어진 것은 아니다. 계정 R13·R14도 이번 문서 반영만으로 인증 코드·DB·권한이 변경되지 않는다. 공유 DB 적용은 대상·백업·복구를 대조한 별도 환경 승인을 받고, 인증/권한·Secret·외부 비용·운영 전환의 별도 승인 경계도 유지한다.
