- A8 기준 실측(2026-10-11, exact 시작 SHA `4dfd6389208ac05f6e53baead7015df65215ea41`): 승인 전용 QA DB에서 등록/미등록 각 4회 교차 순서·개발용 mock으로 동일 `{status:'accepted'}`를 확인했으나, 가입 p50은 기존 50.876ms 대 미등록 297.194ms, 복구 p50은 기존 178.795ms 대 미등록 0.960ms였다. 표본이 작고 로컬↔WSL 터널 측정이라 운영 환경 분포로 일반화하지 않는다. 그래도 처리 경로가 분리된다는 기존 코드 판정과 일치하며, 응답 내용 동일성만으로 계정 존재 추측 방어가 성립하지 않는다. 고유 시험 자료는 정리했고 보호 DB 쓰기는 0이다.
- 영향: 자기 신청 대기·반려 재방문의 새 API와 처리시간 차이 방어를 임의로 출시할 수 없고, 정식 관리자 링크의 실제 수신을 검증했다고 주장할 수 없다. 기존 가입/복구의 mock 권한·실패 닫힘 회귀 및 응답 시간 측정은 계속한다.

## Task 7 — Windows Chrome·Edge 실제 200% 브라우저 조작

- 2026-10-11 추가: 사용자 소유 Chrome 창의 접근성 내용을 읽어 자체 확대를 제어하려는 시도가 사적 화면 접근 위험으로 자동 거부됐다. 입력·창 변경 없이 중단했고 시험용 루프백 Web도 종료했다. 다른 경로로 이 거부를 우회하지 않는다. 실제 200% 검증을 재개하려면 신산님이 분리된 시험 전용 Chrome·Edge 창을 준비해 접근을 명시적으로 허용하거나, 각 화면을 직접 확인한 결과를 제공해야 한다. 준비 전에는 자동 viewport/CSS 증거를 브라우저 자체 200% PASS로 승격하지 않는다.
- 판정: 현재 제어 도구로 만든 Chrome QA 탭에서 `Ctrl++`와 `Ctrl+=`를 시도했으나 페이지의 `devicePixelRatio=1`, `innerWidth=1892`가 변하지 않아 브라우저 자체 200% 확대 증거가 아니다. Edge 실행 파일은 있지만 현재 브라우저 제어 표면에 연결된 Edge가 없어 QA 탭을 열 수 없다.
- 영향: 18개 대표 화면과 계정 화면의 Chrome·Edge 실제 200% 확대, 화면별 가로 넘침·입력/버튼 가시성은 미검증이다. viewport 축소나 CSS zoom으로 PASS를 대체하지 않는다.
- 조치/재개 조건: 독립적으로 가능한 Chrome 공개 계정 화면의 정상·오류 표기 및 Tab 순서를 기록하고 QA 탭·로컬 서버를 정리한다. 실제 브라우저 200%를 조작·확인할 수 있는 Windows UI 제어 또는 신산님의 직접 검증 결과와 Edge 연결이 준비되면 같은 최종 SHA에서 각 화면을 다시 확인한다. 보호 DB·외부 메일·기존 사용자 브라우저 탭에는 영향이 없었다.
